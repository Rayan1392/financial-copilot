# Admin In-App Messages

Status: Gate A: Approved by the owner on 2026-11-22

## Product scope

An authorized Sapio administrator can send an official message to one existing web account. The administrator starts from the current Users directory, searches or filters, and selects the recipient. The recipient can find recent messages and revisit history from the signed-in web workspace. Use the sender label «تیم ساپیو». Keep message content operational. Payment credentials, verification codes, and personalized trading recommendations are outside the intended use.

The initial scope covers immediate, manual, single-recipient delivery in the web app. The administrator can enable replies when starting a support conversation. Service notices are one-way. Users reply from the existing conversation and each reply appears in a shared staff queue. Starting a new conversation from the user inbox, assignment, bulk and scheduled sends, recall, attachments, clickable links, email, Telegram, and browser push are deferred. Inbox access and replies are free for all plans.

On 2026-11-22, the owner agreed to include replies to existing support messages and a shared staff queue, then explicitly approved the Gate A design. See `tasks.md` for the proposed implementation plan and the decisions still open.

Reuse this directory and its visibility rules, including permissions for subscription filters.
- `src/frontend/src/components/app/account-menu.tsx` provides the full and collapsed desktop account menu via `sidebar.tsx`. The signed-in desktop layout is in `routes/_app.tsx`. The separate mobile/PWA account screen is in `routes/m.account.index.tsx`.
- `AuthDbContext` stores Identity, tenant membership and `SecurityAdminAudits`, which lets the send and its audit share one transaction. Features 097 and 099 use separate Telegram delivery and market-alert history semantics. Their worker and history projections have no dependency on this inbox. See `docs/notification-orchestration.md`.

## Interaction design

1. In Customer 360, show «ارسال پیام» for an administrator with send permission. Open the composer with the selected recipient fixed. Show the display name and an account identifier already visible under existing permissions. Use the selected user ID for the command. If the operator changes recipient, reset the compose attempt and require review again. The existing multi-select remains available for its current actions.
2. Require a subject and body, with proposed limits of 120 and 2,000 characters. Offer «امکان پاسخ» at composition, off by default. Preview the chosen reply mode, message and recipient before final confirmation. Disable duplicate submits while pending. On a recoverable failure, preserve the draft and allow a safe retry. On success, show «پیام ارسال شد» and return to Customer 360. Success means the message is committed and available in the recipient's inbox.
3. Add «پیام‌ها» to the desktop account menu. Put a small static dot on the account trigger when there are unread messages, including in the collapsed rail. Show the unread count beside the menu item and cap the displayed count at `۹۹+`. Provide an accessible label for the trigger and a text label for unread rows. The indicator uses no sound, toast, animation, or focus changes.
4. Open a dedicated inbox page inside the workspace at `/messages`. Show one row per conversation ordered by latest message, with subject, Tehran-local date/time and an «خوانده‌نشده» label. Provide «همه» and «خوانده‌نشده» filters and load more on demand. In detail, show the chronological conversation with «تیم ساپیو» and «شما» as author labels. When replies are enabled, offer «پاسخ» and a plain-text composer. Acknowledge displayed staff messages after the conversation opens successfully. Opening the account menu or list preserves unread status. A failed read update keeps the indicator and can be retried. Provide loading, empty, retry and keyboard-navigation states. Confirm Persian RTL layout, wrapping and focus behavior.
5. Proposed mobile parity adds «پیام‌ها» to the mobile account screen and a static dot on the existing mobile account entry point. A dedicated mobile route reuses the data and message presentation with the mobile shell. Map desktop/mobile inbox routes in the existing experience switch.
6. Add a shared «پیام‌های کاربران» section in the existing admin panel. Default to «نیازمند رسیدگی» and offer «همهٔ گفتگوهای پشتیبانی». Show the account identifier under existing visibility rules, subject and latest activity. Order pending conversations by the oldest unanswered user reply. Any authorized operator can open and answer. Opening a conversation preserves its pending status. The item leaves the pending view after a staff reply commits. A new user reply returns it to the queue. If another operator replies or a user adds a message while a draft is open, refresh the conversation and retain the draft for review before submitting again.

## Architecture and persistence

- Implement focused Application use cases for starting a conversation, appending a reply, querying the user inbox and staff queue, and acknowledging staff messages. API adapters derive tenant and actor IDs from the authenticated web session. Application owns eligibility, reply and queue rules. Infrastructure owns EF Core persistence and translates membership/identity state through a port.
- Add `InAppConversations` and `InAppMessages` in the Auth EF Core migration stream. A conversation contains tenant, recipient, subject, reply mode, revision, latest activity and nullable `PendingSinceUtc`. A message contains the conversation ID, per-conversation sequence, authenticated author ID and role, body, send time and idempotency key. Customer-visible author labels follow the role. Message content and original send time are immutable. Each staff entry has a nullable first-read timestamp for the recipient. Index by tenant, recipient and latest activity for inbox paging, by tenant and pending time for the queue, by conversation and sequence for detail paging, and use a partial index for unread staff entries. Store timestamps in UTC and localize at display. Apply the agreed retention policy to the conversation and its messages.
- Append messages and update revision, latest activity and queue status in one transaction. The first unanswered user reply sets `PendingSinceUtc`, further user replies preserve it, and a staff reply clears it. A staff reply includes the detail revision the operator reviewed. On stale revision return `409` with the UI preserving the draft. A duplicate of an already committed send returns the original result even if the revision has advanced. Update read timestamps independently of the conversation revision and only for staff messages in scope with a null timestamp.
- Use a database-enforced idempotency key scoped to tenant and authenticated author. Reuse it on ambiguous failures. Check the original operation, target and normalized content/reply mode to distinguish replays from conflicting reuse. Save a content-free `SecurityAdminAuditRow` for each successful staff send or reply in the same transaction. Audit admin detail access before returning message bodies, using the fail-closed pattern of `AdminContentReadAudit`. Audit identifiers and correlation metadata without message text.
- Validate that the recipient belongs to the administrator's tenant and is enabled and unlocked at send time, using the directory's status semantics. Apply a dedicated rate limit keyed by authenticated sender and tenant. The UI composer requires existing `admin.users.read` and the proposed `admin.in-app-messages.send` permission, and the API enforces both. Grant the new permission through existing role and permission management to designated operators. Verify how mandatory bootstrap permissions and existing role seeds handle the new code before choosing its initial assignment.
- Require `admin.users.read` and a proposed `admin.in-app-messages.support` permission to view and respond to the shared queue within the current tenant. The send permission controls starting conversations. Enforce each permission on the backend and resolve the message recipient from the conversation. Recheck recipient eligibility on staff reply. Apply actor/tenant write rate limits to both sides. Authorize all user operations by `(TenantId, RecipientUserId)` from the signed-in web user and enforce reply mode in the Application. For an absent or out-of-scope ID, return the same `404`. Reject API-key actors. Apply `Cache-Control: no-store` to message responses and exclude them from PWA/persistent caching. Clear private cache entries on logout and account change. Render all content as escaped plain text and exclude message text and contact details from logs, audit details and analytics.
- Use the database as the delivery and read-state source. Count unread staff messages for the user's badge. Refresh on sign-in, tab return, and approximately every 60 seconds while visible and online. Refresh after reading and on inbox opening. Preserve the last successful count within the same session on transient failure. Refresh the staff queue on entry, after staff replies and through bounded polling while the queue is visible. Track aggregate send/reply outcomes, oldest pending age and time to first staff reply without loading message content into telemetry.

## Proposed HTTP contracts

| Method and route | Behavior |
|---|---|
| `POST /api/v1/admin/users/{userId}/in-app-messages` | Starts a conversation with subject, body, reply mode and an idempotency key. Returns the conversation and message IDs after commit. |
| `GET /api/v1/in-app-messages/me/summary` | Returns unread count only, with a bounded query matching the display cap. |
| `GET /api/v1/in-app-messages/me` | Returns cursor-paged conversation summaries with optional unread filter. The cursor is scoped to recipient, tenant and filter. |
| `GET /api/v1/in-app-messages/me/{conversationId}` | Returns detail and a bounded page of messages without changing read state. |
| `POST /api/v1/in-app-messages/me/{conversationId}/replies` | Appends a user reply in a reply-enabled conversation. Requires an idempotency key. |
| `PUT /api/v1/in-app-messages/me/{conversationId}/read` | Accepts a bounded set of displayed staff message IDs. Repeated or concurrent calls preserve first-read timestamps. |
| `GET /api/v1/admin/in-app-messages/support` | Lists support conversations with pending/all filter and cursor. Queue metadata excludes message bodies. |
| `GET /api/v1/admin/in-app-messages/support/{conversationId}` | Returns audited, paged conversation detail with current revision. |
| `POST /api/v1/admin/in-app-messages/support/{conversationId}/replies` | Appends a staff reply with expected revision and idempotency key. The commit clears the pending item. |

Use existing validation and ProblemDetails conventions. Return a validation error for malformed content, a conflict for an ineligible in-tenant recipient or reused key with different data, and a rate-limit response for excessive sends. A passive list load, prefetch or crawler must never write read state. The detail component acknowledges only a user-opened, successfully loaded message.

## Trade-offs and decisions

- Reusing the directory avoids duplicating search and preserves tenant and permission checks. Keeping the action inside Customer 360 adds a click and makes the target explicit, which helps prevent misdirected messages.
- Saving directly to Postgres makes a successful send immediately available in the inbox and avoids a new delivery dependency. The passive badge can lag by the refresh interval. Consider streaming only if a later requirement calls for lower latency.
- Pending state follows unanswered user activity. This keeps the queue shared and defers assignment and close/reopen controls. Staff need an operating owner and a response expectation before exposing replies to customers.
- Owner decisions are recorded in `specs/open-questions.md` under OQ-125 through OQ-129. Open items cover mobile scope, retention, initial role assignments and queue ownership. Time-to-badge and API cost still need measurement in a running environment.

## Preliminary delivery sequence and verification

1. Resolve the Gate A decisions and agree on the recipient, send, read and retention rules.
2. Define contracts, persistence, access policy and transactional send/reply. Verify the migration and role seed against existing Auth data. Test concurrent retries, stale revisions, audit failure, and the transition from a pending reply to a committed staff answer.
3. Connect the Customer 360 composer to the send endpoint. Verify reused search/filter, recipient preview, keyboard interaction, error recovery and permission gating. Test direct requests with missing permissions, API-key credentials, ineligible recipients and another tenant's user ID.
4. Build the inbox, count indicator and read-state flow. Verify that a second user and other tenants cannot list, fetch or acknowledge a message. Test concurrent reads, stable cursor paging, session change, empty/offline/error states, dark theme and both desktop sidebar variants. Test the mobile/PWA layout if included by Gate A.
5. Connect user replies and the staff queue. Verify that users cannot initiate a new conversation or reply to a one-way notice. Verify that a different authorized staff member can answer, opening the item preserves its pending status, the committed answer clears it, and the next user reply adds it back. Cover cross-tenant and unauthorized staff requests and concurrent operator replies.
6. Walk through send → unread → open → user reply → staff queue → staff answer → unread again → history after reload or second-device sign-in. Check query plans and refresh traffic with representative data. Compare backend and frontend checks against `specs/test-baseline.md`.
