# Feature 164 — measurement of the conversation-log queries (2026-11-20)

Task 7.1 of `tasks.md`. Synthetic data only; the agent has no production access. Production check: `production-explain-readonly.sql` (task 7.2).

## Setup

- PostgreSQL 17.12 (`postgres:17-alpine`, throwaway Docker container, default settings: `shared_buffers` 128MB, `work_mem` 4MB, JIT on), on the developer laptop while nothing else heavy ran.
- Schema: `schema-from-migrations.sql`, generated by `dotnet ef migrations script` for `ConversationDbContext` (existing indexes: `PK_Messages`, `IX_Messages_ConversationId_CreatedAt`, `PK_Conversations`, `IX_Conversations_TenantId_ActorId_UpdatedAt`).
- Data: `seed-synthetic.sql` — 50,000 conversations, 493,945 messages (249,739 questions), 4,990 users with conversations, 180 days ending 2026-11-20; `Messages` 245 MB. The 30-day window holds 40,894 questions (39,993 in the measured tenant).
- Queries: `explain-queries.sql`, the count and page SQL exactly as `EfCoreAdminConversationLogQueries` builds it (generated from one template with the production script), each in `BEGIN; SET TRANSACTION READ ONLY; SET LOCAL statement_timeout = '5s'; EXPLAIN (ANALYZE, BUFFERS) …; ROLLBACK`. Three runs; the table shows the median `Execution Time`; plans below are from the third run.

## Findings

1. **Default page (A) is under the 300 ms budget** (195 ms count + page) but its plan is a sequential scan of `Messages` plus a sort, which meets the second condition of the 8.1 rule. With the index: 75 ms. See `index-decision.md`.
2. **The status-filtered count can exceed the 5 s statement timeout.** `status=Failed` over 30 days took 8,837 ms uncapped, so the API would return an error (statement timeout) for this filter on a data volume like this one. The cost is the per-turn answer lookup and the JSON extraction of `Outcome` for every turn in the window (about 0.14–0.18 ms per turn in the `Result` node, plus about 0.7 s of JIT compilation). An index does not change it (the scan of the questions is a small part). The page for the same filter is fast (it stops after 20 matches).
3. **Answer lookups before the sort.** When the planner expects few rows (text search B, user filter D) or needs many (page 50, E), it runs both lateral lookups — including the `Outcome` extraction — for every candidate turn and sorts afterwards (3,304 turns for B, 879 for D, 1,000 for E). The default page (A) sorts first. This is a query-shape issue, not an index issue: with the index, B became slower (the bitmap scan still feeds all matches into the lookups).
4. **NoResponse page (C2) is slow** because the page query extracts `Outcome` for every scanned turn although the filter only needs `AnswerId IS NULL`.
5. Page 50 (E) spills its sort to disk with the default `work_mem` (4MB); harmless at this size.

| C1 count: payload parsed once per turn | 4,361 | 5,192 |
| C1 count: parsed once, JIT off | 3,319 | 4,159 |
| C2 count: current SQL, JIT off | 750 | 895 |
| C1 count: lookup returns the raw payload, outer `LIKE '%"Outcome":7%'` pre-filter, then the full check (no index) | 2,639 | — |
| C1 count: set-based (window function over the window's messages, no per-turn lookup; no index) | 5,928 | — |

Single flat scans of the 39,959 answers in the window (one run, JIT off): reading the payload 355 ms; `pg_input_is_valid(…, 'jsonb')` 416 ms; one `::jsonb ->> 'Outcome'` 599 ms; the full current `Outcome` expression 6,804 ms; the same with `json` instead of `jsonb` 5,053 ms. The current expression costs about ten times one parse.

Reading of the experiments: picking the page first fixes findings 3 and 5 (6–286 ms with the index). No SQL-only variant brings the status-filtered count under about 2.5 s at this volume, because every turn in the window needs its first answer and its outcome. Options for the owner are in `index-decision.md`; none was applied.
