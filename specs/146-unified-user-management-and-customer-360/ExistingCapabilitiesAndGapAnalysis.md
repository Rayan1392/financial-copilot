# Feature 146 — Existing Capabilities and Gap Analysis

## Investigation basis

This is a static repository review based on specifications, implementation reports, code graph results, and source files listed below. No application was started, no external provider was called, and no database connection or migration state was checked.

Capability labels describe repository evidence, not live deployment state:

1. Implemented and verified — code and repository test/report evidence exist.
2. Implemented but incomplete or unverified — local code exists, with operational or integration gates outstanding.
3. Partially implemented — a useful part exists, but the requested workflow is incomplete.
4. Specification only — design exists without matching implementation evidence.
5. Missing — no implementation was found for the requested capability.

## Repository evidence

### Identity and provider links

- src/backend/FinancialCopilot.Infrastructure/Authentication/Persistence/AuthPersistenceModels.cs: FinancialCopilotUser is a thin ASP.NET Identity user with IsEnabled. RefreshTokenRow stores user, tenant, token digest, issue/expiry/revocation, and authentication-method data. There is no dependable registration timestamp or last-successful-login timestamp/provider on the user record.
- src/backend/FinancialCopilot.Infrastructure/Authentication/Persistence/TahlilAppPersistenceModels.cs: TahlilAppExternalIdentityRow maps provider and external user ID to a local user and tenant, tracks Active/Suspended/Revoked state, launch and entitlement-sync state. UserProfileRow stores names and encrypted national ID/mobile values with last-four display fields. Feature 139 defers admin profile display/reveal, so no profile field is searchable or unmasked in the MVP.
- src/backend/FinancialCopilot.Infrastructure/Authentication/TahlilApp/TahlilAppProfileProtector.cs: field-level ASP.NET Core Data Protection is used for national ID and mobile. Ciphertext is not a matching key. Feature 139 requires a persistent, backed-up, shared key ring and says the status contract carries no profile PII.
- src/backend/FinancialCopilot.Infrastructure/Authentication/Persistence/AuthDbContext.cs: AuthDbContext owns local users, tenant memberships, refresh sessions, Telegram links, TahlilApp identities, and user profiles. The TahlilApp identity migration is 20261017135632_AddTahlilAppIdentityAndProfile.
- src/backend/FinancialCopilot.Infrastructure/Authentication/TelegramLinkService.cs and AuthDbContext.cs: Telegram links are actor/tenant scoped; revoked rows are retained; active Telegram identity and actor uniqueness are enforced. Telegram usernames are not stable identity keys.
- Feature 139 Design revision 6 and ImplementationReport supersede earlier credit-policy questions. Contract v2 requires an authoritative UTC subscription.effectiveFrom; external deployment and round-trip verification are pending. T-24 admin masked-profile/reveal and T-28 explicit account-linking work remain deferred.

### Admin API and UI

- src/backend/FinancialCopilot.API/Controllers/AdminManagementController.cs: GET /api/v1/admin/users accepts only search and limit; GET /api/v1/admin/users/{userId} returns the same basic view. Routes use existing narrow permission policies and authenticated web-user authorization.
- src/backend/FinancialCopilot.Infrastructure/Administration/EfCoreAdminManagementService.cs: SearchUsersAsync tenant-scopes through Auth user memberships, searches email only, orders by email, and applies a bounded limit. Existing methods perform audited account status changes and session revocation.
- src/backend/FinancialCopilot.Application/Administration/AdminManagementContracts.cs: AdminUserView contains UserId, Email, IsEnabled, IsLockedOut, roles, and tenant IDs. It does not contain acquisition, provider links, registration/login dates, subscription, balance, or purchase summary.
- src/frontend/src/components/admin/admin-page.tsx (UsersPanel) and src/frontend/src/integrations/financial-copilot/admin-client.ts (users): the UI searches by email, requests a fixed 50 users, and displays email/status/roles with an inline detail panel. It has no Customer 360 sections or provider/acquisition filters.
- specs/037-frontend-admin-panel/tasks.md explicitly records the customer-account lookup entry point as a gap. Feature 037's completed UI does not add a user-to-Billing-account directory.

### Billing and activity

- src/backend/FinancialCopilot.Infrastructure/Billing/Persistence/BillingPersistenceModels.cs (CustomerAccountRow): account rows include tenant, optional UserId, account type/mode, current plan/effective dates, and subscription revision. The user-to-account relationship is owned by Billing.
- src/backend/FinancialCopilot.Billing/Accounts/WalletSnapshot.cs, src/backend/FinancialCopilot.Billing/Usage/UsageLedgerEntry.cs, and Billing persistence services: wallet projections, reservation/commit/release, and immutable charge/refund/adjustment entries are implemented. Available, reserved, credit-line capacity, source allocation, and expiry must not be collapsed into a naive sum.
- AdminManagementController.cs: subscription reads/writes, bounded usage-ledger reads, credit adjustment, and security/Billing audit routes already exist keyed by Billing customer account ID. They are permission-gated, tenant-scoped, audited for mutations, and do not allow direct wallet editing.
- src/backend/FinancialCopilot.Billing/Purchases/BillingPurchaseModels.cs (BillingCheckoutIntent) and BillingPurchaseUseCases.cs: local checkout/order records include actor, customer account, product/version, amount/currency, payment reference, status, dates, and version. Feature 098 supports manual receipt review and callback/reconciliation states. This data is not proof of a TahlilApp purchase; checkout/entitlement records alone are not revenue.
- There is no implemented user-level usage analytics dashboard or Customer 360 purchase-history screen. Existing ledger and Billing records can supply a bounded read model without duplicating them.

## Reuse and implementation boundaries

- Reuse Features 002, 031, 035, and 037 for Identity, tenancy, permissions, audit, frontend shell, and safe user actions.
- Reuse Features 010 and 013 for Billing account, wallet, reservation, ledger, usage, subscription, and financial ownership.
- Reuse Features 087, 098, 139, and 145 as provider-specific or credential workflows; Customer 360 reads their state and does not replace them.
- Extend the existing Admin Management API and React admin route. Do not introduce a parallel user table, Billing calculation, admin system, microservice, event bus, or independent frontend.
- Add only one Identity metadata row for facts that have no reliable source today. Keep provider-specific identity lifecycle and Billing state in their owning contexts.
- Build Customer 360 as a read-only composition query. Its mutations remain the existing Admin and Billing commands.
