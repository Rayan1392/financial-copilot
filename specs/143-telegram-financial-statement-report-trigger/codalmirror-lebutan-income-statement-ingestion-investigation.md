## 3. Actual Admin path and shared ingestion

The Admin UI posts `AdminManualNoavaranFinancialStatementBackfillRequest` (`Symbol`, `FiscalYearEnding`, `PeriodMonths`, `StatementType`) to `NoavaranFinancialStatementBackfillController.Run` at `POST /api/v1/admin/noavaran-current/financial-statement-backfill/single-company-period`. The controller validates the inputs, looks up exact `NoavaranEligibleCompanies.TseSymbol`, and calls the **same** `ManualNoavaranFinancialStatementBackfillService.ExecuteAsync` for one category. It returns `Persisted`/`AlreadyExists`/`Empty`, HTTP 500 for persistence failure, or HTTP 502 for provider failure. See `src/backend/FinancialCopilot.API/Controllers/NoavaranFinancialStatementBackfillController.cs` and `src/backend/FinancialCopilot.Infrastructure/Financial/Ingestion/NadpcoApi/ManualNoavaranFinancialStatementBackfillService.cs`.

The shared service fetches before invoking `FinancialDataSyncProcessor.ProcessPayloadAsync`. It builds the run idempotency key from company, category, fiscal year, period, and **payload checksum**. The provider uses `POST api/v2/FS/IncomeStatement/Values` with JSON `companyIds:[<id>], items:[]` and query `fromYear`, `toYear`, `perTId`; nullable configured `isAudited`, `isRepresented`, and `isComposing` filters are appended when present. It has no exact `PeriodEnd` or source report ID request parameter. `ReadSuccessfulPayloadAsync` accepts any HTTP success body; it does not assess statement completeness. Timeout and HTTP retry policy come from provider configuration, not from Feature 143.

`FinancialDataSyncProcessor.ProcessCoreAsync` persists a `Running` run, stores the raw payload, invokes the normalizer, and sets `Completed` with `ProcessedRecords` equal to the **number of typed statements**, not line items. Its effective-completion check for non-monthly datasets is `Status == Completed`; there is no financial-statement item check. `NadpcoApiFinancialStatementNormalizer.NormalizeAsync` upserts each header and calls `SaveChangesAsync`, then upserts its line items and calls `SaveChangesAsync` again, with no encompassing transaction in this method. A later exception can therefore leave earlier headers/items persisted while the run is marked `Failed`. Source-item identity is now preferred in the **pre-existing working-tree edit**; production deployment is unknown. A changed provider payload checksum allows another manual run; identical completed payload is `AlreadyExists`.

### 10.4 Earliest divergence and causal chain

The **earliest proven divergence is the provider response content** at the same Noavaran endpoint: 26 items at 10:58 versus 47 at 11:22, with identical report identity/parameters and unchanged overlapping values. This is provider **data-availability/propagation timing**, not evidence that the source provider malfunctioned. The first response was an HTTP success containing a valid but incomplete report object.

`ManualNoavaranFinancialStatementBackfillService.ExecuteAsync` treats one processed report as `Persisted`. `FinancialDataSyncProcessor.ProcessCoreAsync` marks the run `Completed` based on report count, and `TelegramChannelFinancialStatementHandler.ValidatePersistedPeriodAsync` checks report header identity but **not item coverage**. `HandleRecognizedAsync` then stores `Feature143:Completed`. That checkpoint suppresses replay, and no delayed completeness reconciliation follows. The Admin call succeeded because it fetched a newly populated raw response 24m27s later; the checksum changed, so the shared processor executed normalization/upsert again. The later generic scheduled sync also refreshed the same source report.

The previous duplicate metric-code defect is **not this incident's cause**: the target 10:58 and 11:22 runs both completed with zero errors, and the six missing approved IDs were absent in the first raw response before normalization. There is no evidence of an exception, validation rejection, pagination limit, zero-as-null conversion, or Feature 144 arithmetic/selection error causing these six absent items. The first report's exact historical persisted line count cannot be reconstructed because item rows have no creation/sync timestamps, but the missing six cannot have been normalized from that first raw payload.

### 10.5 Reproduction and corrective-action boundary

The pair of retained Production payloads is a deterministic regression fixture: for the same report identity and request, the first successful response has 26 items (9/15 approved); the later successful response has 47 (15/15 approved), adding 21 IDs without changing any of the first 26 amounts. A regression should assert that Feature 143 does not permanently complete the first response and that a bounded delayed re-fetch uses the changed checksum to upsert the same report, preserving separate scope and legitimate zeros. No full raw payload or credential needs to enter the repository.

At the time of Production inspection, no code or Production data had been changed. A fixed requirement that every legitimate income report has all 15 approved IDs would be unsafe; a scoped comparison with earlier same-company report coverage can flag **suspected** incompleteness for bounded reconciliation without discarding data. The local implementation and explicit retry/review policy are recorded in Section 10.6. The deployed code still has no delayed Feature 143 reconciliation mechanism.

All Production inspection was read-only. No provider call, resync, backfill, checkpoint update, database mutation, service restart, commit, push, or deploy was performed.

### 10.6 Local corrective implementation and verification

The local Feature 143 handler now treats a six-month Noavaran Income Statement as **suspected incomplete** when its persisted approved source IDs omit IDs already present in that same company's matching three-month income report (same provider, period start, scope, audit and restatement flags). It still persists the first response, including zero-valued items, but records `ReconcilePending` under `Feature143:Partial` instead of permanently completing the checkpoint. This is a comparison with observed company data, not a universal requirement for all 15 approved IDs. Reports without a comparable prior period retain the existing behavior.

The API now scans these pending checkpoints every five minutes. It re-fetches no earlier than 30 minutes after the first response and, if still incomplete, once more no earlier than 60 minutes after the first retry. The per-category maximum remains three attempts. A fuller response follows the shared checksum/upsert path; after the approved coverage catches up, the checkpoint becomes `Feature143:Completed`. If coverage remains short after the final attempt, it becomes `Feature143:ReviewRequired`. The original announcement and category outcomes are stored in the checkpoint for this recovery; category claims use the existing compare-and-swap transition to avoid duplicate concurrent retries. The worker runs only in the API host, under the existing Feature 143 auto-backfill enablement and channel/tenant controls.

Regression evidence: the new six-month test was first observed failing against the former header-only completion logic, then passed after the change. A second test starts with nine approved items (including a legitimate zero), advances the clock past the retry delay, and verifies that the later 15-item response updates the same report and completes the same checkpoint. A third test verifies the two delayed attempts stop at `ReviewRequired` when the response stays sparse. The Feature 143 handler suite passed **17/17**. The related Feature 143 end-to-end, Admin backfill, and Feature 144 PostgreSQL integration slice passed **11**, skipped **4**, failed **0**; skipped tests did not execute their PostgreSQL assertions. The Release API build passed with **0 warnings, 0 errors**.

This local change does not retroactively re-open Production checkpoint `bd16cc06-59ad-4c69-9ad2-c35894b36029`, which is already `Completed`; that report was refreshed by the subsequent Admin/generic sync. No local code was committed or deployed. All Production access in this follow-up remained read-only.
