# Feature 126 Observability Remediation Plan

Status: `READY_FOR_IMPLEMENTATION_REVIEW`

## Scope and blocker

The only remaining production blocker is that `Feature126OperationalSummaryRegistry` is
process-local, capped in memory, and not externally observable. A worker restart or crash can
remove the only recent run evidence and does not by itself produce a production alert.

This plan defines the implementation boundary for durable run evidence, worker health/readiness,
and external monitoring. It authorizes no code change, migration, or specification change in this
document.

## 1. Durable run evidence

### 1.1 Evidence model

Treat each scheduled attempt as one durable run record keyed by `run_id`/correlation id. The
record is written to an approved durable, queryable operational telemetry sink with retention
appropriate for production incident investigation. The sink may be an OpenTelemetry-compatible
collector and log/trace backend, or the platform's equivalent durable structured-event store. It
must acknowledge writes independently of the worker process and must not be an in-memory exporter.

The process-local registry may remain as a best-effort recent-read cache, but it is never the
source of truth for health, recovery, incident response, or dashboards.

Each run emits:

- a `run_started` event before provider work;
- heartbeat/checkpoint events while work is active, including the latest bounded counters;
- exactly one terminal event when the live fenced owner can finalize; and
- a recovery/finalization event when a later worker observes an expired `Running` lease.

Events are idempotent by stable `event_id` and are replayed/queryable by `(run_id, event_sequence)`;
all carry a schema version. A terminal event
is immutable. Checkpoints are monotonic and may be compacted by the telemetry backend only after
the terminal record has been retained.

#### O-01 — Run lineage and retry contract

- `run_id` is formatted as `fx126-{tehran_date:yyyyMMdd}-{ulid}`. The ULID is generated by the
  currently fenced Feature 126 worker after it acquires the `feature126` lease. It is globally
  unique, sortable by allocation time, and is never reused.
- The fenced worker owns allocation, but allocation is not evidence of a run by itself. The worker
  must first persist `run_started` to the durable sink and wait for its acknowledgement. That
  acknowledgement is the persistence point after which the attempt may start provider work.
  Failure to persist or acknowledge `run_started` leaves the attempt non-started and provider work
  is prohibited.
- Every run carries nullable `recovered_from_run_id` and an `attempt_reason` of `scheduled`,
  `retry`, or `takeover`. A recovery or takeover always creates a new run and sets
  `recovered_from_run_id` to the immediately superseded run. The link is written in the new
  `run_started` event, not inferred later from timestamps.
- Each execution attempt is a new run, including a retry after a terminal failure, timeout, or
  handoff failure. A retry does not append a second terminal lifecycle to the old run. It links to
  the prior run and reuses the existing same-day fact and handoff idempotency rules.
- A crashed or expired owner is recovered only after the existing lease fence permits takeover.
  The recovering worker creates its new run, durably records the link, then records the old run as
  `LeaseLost` with termination code `RecoveredByNewRun` if that terminalization is accepted by the
  sink. The old run is never rewritten as successful. If the old owner later reports, those events
  remain stale-owner evidence and cannot change either run's authoritative outcome.
- The lineage is therefore a chain of independent attempts: a run has at most one immediate
  predecessor in `recovered_from_run_id`; the predecessor remains queryable and immutable after
  takeover or retry. No run-history table is introduced.

#### O-02 — Event ordering and lifecycle authority

- The Seq-backed Feature 126 append contract is the single ordering authority for each `run_id`. The
  worker does not invent sequence numbers locally. Its append request contains a stable `event_id`,
  expected predecessor state, owner/deployment identity, fencing token, and event payload. The
  durable append operation atomically de-duplicates an already accepted `event_id`, verifies the
  expected predecessor and live fence, allocates the next `event_sequence`, and appends the event
  to Seq. No worker replica, process-local registry, or PostgreSQL row allocates event order.
- `event_sequence` starts at 1 for `run_started` and increases by exactly one for every accepted
  event in that run. A retry of the same append returns the original sequence and acknowledgement;
  a new logical event cannot reuse a sequence. The resulting `(run_id, event_sequence)` is the
  replay and query ordering key.
- The allowed transitions are: no state → `Running` (`run_started`); `Running` → `Running`
  (`heartbeat`/`checkpoint`); `Running` → `Handoff` (`handoff_started`); `Handoff` → `Handoff`
  (`heartbeat`/`checkpoint`); `Running` or `Handoff` → one terminal state (`Success`,
  `PartialSuccess`, `Failed`, `Cancelled`, `Timeout`, `LeaseLost`, or `HandoffFailed`). A recovery
  event on the old run may only close it as `LeaseLost`; the new run starts independently at
  `Running`.
- An event from a worker whose fencing token is no longer current is accepted only as a marked
  `stale_owner_event` for diagnostics, with no lifecycle, counter, handoff, or terminal-state
  mutation. The database lease fence remains authoritative for fact writes and handoff.
- A duplicate terminal submission with the same `event_id` or identical terminal payload is an
  idempotent success returning the original acknowledgement. A different terminal payload after
  terminalization is rejected as `terminal_conflict`, raises the telemetry failure metric, and
  leaves the first terminal event immutable.
- An event whose expected predecessor does not match the current state, or whose sequence cannot
  be the next sequence, is rejected as `out_of_order`; it is not applied retroactively and does not
  advance the stream. The worker reloads the current run state and either retries the same logical
  event with its original `event_id` or stops as stale/lost. Terminal events are never accepted
  after another terminal event.

### 1.2 Required run identity and fields

The durable run record must contain these fields, using the existing canonical summary names where
they already exist:

| Field | Required semantics |
|---|---|
| `run_id` / `CorrelationId` | Stable unique identity for one scheduled attempt; also the trace/correlation identity. It is not the Tehran date and is never reused after takeover. |
| `tehran_date` | Current Tehran calculation day used for same-day idempotency. |
| `deployment_id` | `DeploymentIdentifier` of the worker instance/deployment that owns the attempt. |
| `configuration_revision` | Candidate configuration revision evaluated by `Feature126ActivationGuard`. |
| `lease_name` | `feature126`; included to correlate evidence with the existing distributed lease. |
| `fencing_token` | Current owner token, redacted or hashed in general-purpose logs but available in the restricted operational record for takeover correlation. |
| `lifecycle_state` | `Disabled`, `ActivationGuardRejected`, `CurrentDaySucceededNoOp`, `Running`, `Handoff`, `Success`, `PartialSuccess`, `Failed`, `Cancelled`, `Timeout`, `LeaseLost`, or `HandoffFailed`. Unknown values are rejected by the schema contract. |
| `lease_status` | `NotAttempted`, `Owned`, `Recovered`, `Lost`, or `Contended`. |
| `outcome` | Normalized `success`, `partial_success`, `failure`, `cancelled`, `timeout`, `lease_lost`, `handoff_failed`, or `no_op`; derived from terminal lifecycle state and not inferred from facts or logs. |
| `failure_code_counts` | Complete fixed-key map from `Feature126FailureCodes.Ordered`; absent failures are zero for a started run and null/not-applicable for a non-started run. |
| `endpoint_counts` | Fixed map for `PSGauge`, `PEGauge`, and `EquilibriumGauge`, each with `Attempted`, `Succeeded`, and `Failed`. |
| `metric_counts` | Fixed map for the three metric kinds, each with `Accepted`, `Unchanged`, and `Failed`. |
| `handoff_status` | `NotApplicable`, `Succeeded`, or `Failed`; handoff success is recorded only after Feature 125 accepts the fenced handoff. |
| `eligible_companies` / attempted/succeeded/failed counts | Bounded aggregate counts only; no symbol or ISIN list is emitted. |
| `published_count` / `inconclusive_count` | Nullable downstream handoff result counts when available; Feature 126 does not calculate or publish them. |
| `started_at_utc` / `completed_at_utc` | UTC lifecycle timestamps with millisecond precision. `completed_at_utc` is null until terminal finalization. |
| `last_heartbeat_at_utc` | UTC timestamp of the latest successful lease heartbeat/checkpoint. |
| `duration_milliseconds` | Set only after terminal completion. |
| `termination_code` | Canonical terminal reason, including `LeaseLost`, `Cancelled`, `HandoffFailed`, or `UnexpectedFailure` where applicable. |
| `event_sequence` / `schema_version` | Monotonic event ordering and compatibility version for replay and deduplication. |

Credentials, authorization headers, raw provider payloads, exception collections, symbol/ISIN
lists, and unbounded exception text are prohibited from the durable evidence record.

### 1.3 Crash and restart behavior

1. On acquisition, the worker writes the `Running` lease envelope and `run_started` evidence. The
   existing `IndustryRelativeValuationSourceLeases` row remains the authoritative fencing/recovery
   gate.
2. During processing, the worker renews the existing lease and emits a bounded heartbeat/checkpoint
   at the same operational cadence. The checkpoint contains the latest counts and timestamps, not
   provider payloads.
3. If the worker crashes, the lease row remains `Running` until `ExpiresAtUtc`. No success is
   inferred from accepted source facts, a missing process, or an absent terminal event.
4. After expiry, a new owner records a `Recovered`/`Running` transition with a new `run_id` and
   fencing token, linked to the abandoned run id. It emits an `abandoned_run_recovered` event for
   the old run and retries the current Tehran day under existing idempotency rules.
5. If the old owner later emits anything, the telemetry sink records it as stale-owner evidence;
   the database fence remains authoritative and rejects stale fact writes, handoff, and terminal
   finalization.
6. A successful or partial-success handoff is finalized with the existing `Succeeded` terminal
   marker. A crash after handoff but before marker commit remains retryable; immutable source facts
   and Feature 125 same-date idempotency make the retry safe.
7. A failed, cancelled, timed-out, lease-lost, or handoff-failed terminal state is written only
   while the worker still owns the live fence. Otherwise the durable record remains an abandoned
   running attempt and is finalized by the recovering owner.

#### O-03 — Fail-closed telemetry behavior

- Provider work cannot start until the durable sink acknowledges `run_started` for the current
  `run_id`. Readiness alone is not sufficient because the sink can fail after startup.
- Handoff cannot start or be submitted unless the sink has acknowledged the preceding
  `handoff_started` event and all required checkpoints for the bounded work have been acknowledged.
  Handoff success/failure must itself be durably acknowledged before the run is considered
  terminal.
- If the exporter or sink becomes unavailable during a run, the worker stops beginning new provider
  calls, stops handoff, and attempts a bounded retry of the required evidence. It does not continue
  ingestion on the basis of console logs, the process-local registry, or an unacknowledged local
  queue.
- Queue overflow, acknowledgement timeout, authentication failure, or a non-success sink response
  is treated as telemetry unavailable. Required-event buffering is bounded; once full, the worker
  fails closed and marks readiness false. Best-effort metrics may be dropped, but required run
  evidence may not be dropped or silently sampled.
- When the sink becomes available, the worker verifies the last acknowledged event and current
  lease/fencing state before resuming. It emits a durably acknowledged recovery/checkpoint event,
  then resumes only if the run is still owned and within its deadline; otherwise it records or
  awaits takeover and starts a new linked run. Missing acknowledgements never get invented locally.

The backend must retain both the latest materialized run view and the append-only lifecycle events
long enough to investigate at least the configured operational retention window. Querying the latest
run view must work after process restart and across worker replicas.

### 1.4 O-04 — Concrete telemetry sink contract

The production sink for Feature 126 is **Seq 2024.x or later, deployed as the internal durable
structured-event store**, reached by the worker through its HTTPS ingestion API. Serilog remains the
worker logging foundation, but required Feature 126 lifecycle events use a dedicated awaited sink
client so their acknowledgement is not confused with console or ordinary best-effort logging.

- Retention is 730 days for Feature 126 lifecycle events and materialized run views. Retention is
  configured in Seq and is not implemented by deleting database data. Payloads are bounded by the
  evidence fields above; secrets and provider payloads remain prohibited.
- The endpoint, API key, TLS validation settings, tenant/environment stream, schema version, and
  retention policy are supplied through secret-backed configuration. API keys are never committed
  to repository settings or emitted in logs. The worker uses a dedicated write key; dashboards and
  incident responders use a separate read-only key/role.
- Delivery is synchronous for required lifecycle events: an event is acknowledged only after Seq
  returns a successful ingestion response for the complete structured event and the client has
  accepted that response. The process-local registry and Serilog console output are not
  acknowledgements and are not fallback sources of truth.
- The client retries transient network failures, HTTP 408/429, and HTTP 5xx with bounded exponential
  backoff and a maximum elapsed retry budget. Authentication, schema, payload-size, and other
  permanent errors fail closed immediately. On exhaustion, the rules in O-03 apply.
- The append contract carries `schema_version`, `event_id`, `run_id`, `event_sequence`, lifecycle
  state, predecessor state, owner/deployment identity, and fencing token reference. Schema changes
  are additive within a major version; incompatible changes increment the major version and require
  a reader/dashboard rollout before the worker emits the new version. Unknown major versions are
  rejected rather than silently misread.
- Seq provides the query API for the materialized latest-run view and append-only event stream.
  The Feature 126 dashboard queries Seq for run timelines, terminal outcomes, failure codes, and
  drill-down links from alerts. Low-cardinality counters and gauges may also be exported to the
  existing metrics system, but those metrics never replace Seq evidence.
- Seq acknowledgement is an ingestion acknowledgement, not a claim that provider work, database
  facts, or Feature 125 handoff succeeded. Those outcomes are represented only by the explicitly
  ordered lifecycle events after their own durable evidence is available.

## 2. Worker health and readiness

### 2.1 Readiness conditions

Feature 126 is ready to receive scheduled work only when all of the following are true:

- the feature is enabled and activation guard inputs contain a non-empty configuration revision and
  deployment identifier;
- owner activation is non-conflicting: Feature 114's legacy P/S owner and the NADPCO Feature 125
  trigger are disabled before Feature 126 activation;
- the database is reachable and the `feature126` lease row can be read;
- durable telemetry export has a healthy connection/queue and has acknowledged the startup evidence
  within the bounded startup timeout;
- the worker can renew its lease/heartbeat on schedule; and
- no unrecovered fatal initialization error prevents the next scheduled attempt.

Readiness means “the worker can safely start or resume bounded ingestion.” It does not mean that
the latest run succeeded, that all source facts are fresh, or that Feature 125 has published a
result.

### 2.2 Unhealthy conditions

Report the worker unhealthy when any of these persists beyond the configured grace period:

- the worker is enabled but no heartbeat is observed within the heartbeat timeout;
- the active lease cannot be renewed, the fencing token is lost, or ownership is contended beyond
  the expected acquisition window;
- durable run evidence cannot be exported or acknowledged;
- the database/lease store is unavailable;
- the current Tehran day has no terminal run after the allowed schedule/retry window;
- a run is stuck in `Running` or `Handoff` beyond its configured deadline;
- repeated terminal `Failed`, `Timeout`, `LeaseLost`, or `HandoffFailed` outcomes exceed alert
  thresholds; or
- activation is rejected because configuration or deployment identity is missing or conflicting.

`PartialSuccess` is not a worker process failure by itself. It is a visible run outcome; alerting
may classify it according to the configured tolerance, while Feature 125 remains responsible for
calculation readiness from persisted facts.

### 2.3 Heartbeat semantics

- The heartbeat is a lease renewal plus a durable operational heartbeat event, not merely a log
  line.
- It is emitted while work is active and during the handoff phase, before the lease safety margin
  is exhausted.
- Each heartbeat includes `run_id`, deployment/configuration identity, lifecycle state, current
  fencing token reference, `last_heartbeat_at_utc`, and bounded progress counters.
- A successful database lease renewal without a durable heartbeat acknowledgement is insufficient
  for “healthy”; the worker must expose telemetry backpressure as unhealthy before evidence is
  silently lost.
- After terminal finalization, heartbeats stop and the terminal event becomes the liveness record
  for that run.

### 2.4 O-05 — Worker health contract

- The Worker hosts a separate internal ASP.NET Core management listener on the configured
  management address/port. It exposes `GET /health/live`, `GET /health/ready`, and `GET /metrics`.
  These endpoints are internal-only, protected by network policy, and are not part of the public
  API or Feature 114 UI contract.
- `/health/live` answers whether the worker process and host are running. It returns HTTP 200 while
  the process is functioning, including when Feature 126 is disabled or the telemetry sink is
  unavailable; it returns failure only when the host cannot service the probe or is in terminal
  shutdown.
- `/health/ready` exposes one of `disabled`, `starting`, `ready`, `degraded`, `lease_lost`,
  `telemetry_unavailable`, `database_unavailable`, or `stopping`, with HTTP 200 only for `ready`
  and `disabled`. An enabled worker is not ready unless the database, lease gate, durable Seq sink,
  and startup evidence acknowledgement satisfy the readiness conditions above. The response
  includes no secrets and includes only bounded state, last acknowledged event time, and current
  run/Tehran-day identifiers where present.
- `/metrics` publishes the required low-cardinality Feature 126 metrics, including readiness,
  health, heartbeat age, exporter state, lease state, and run outcomes. It must not expose
  symbol/ISIN, run id, deployment id, exception text, or provider payload as a metric label.
- On startup, the worker reports `starting`, validates configuration and dependencies, and does not
  acquire a Feature 126 lease or begin provider work until the management listener is active and
  `run_started` can be durably acknowledged. A startup failure leaves readiness false and causes
  the host supervisor to restart or page according to deployment policy.
- On graceful shutdown, readiness changes to `stopping` before new scheduled work is accepted. The
  active run stops at a safe bounded checkpoint, emits a durably acknowledged shutdown/lease-loss
  event when possible, releases ownership according to the existing lease contract, flushes the
  required sink client within the shutdown deadline, and then allows liveness to terminate. A hard
  process crash is handled by lease expiry and O-01 takeover rules.
- When Feature 126 is disabled, liveness remains healthy and readiness reports `disabled` rather
  than an operational failure. The worker does not acquire the Feature 126 lease, emit scheduled
  run evidence, or call the provider. Disabled mode does not make the Feature 126 schedule appear
  successfully completed.
- A telemetry outage changes an enabled worker to `telemetry_unavailable`, makes readiness false,
  prevents provider work and handoff, and raises the durable-evidence alert. Liveness remains a
  process signal; it must not be reported healthy as a substitute for readiness.
- Lease loss changes readiness to `lease_lost`, stops provider work and handoff immediately, and
  prevents success or partial-success finalization by the stale owner. The worker may emit a
  stale-owner diagnostic event only under O-02, then exits the attempt and lets the recovering
  owner create the linked run.

## 3. External monitoring

### 3.1 Metrics

Expose low-cardinality metrics with feature, lifecycle state, outcome, endpoint, and failure code
labels only. Never use symbol, ISIN, provider point id, correlation id, deployment id, or exception
text as metric labels.

Required metrics:

- `feature126_runs_started_total`
- `feature126_runs_terminal_total` by outcome and lifecycle state
- `feature126_run_duration_ms` histogram
- `feature126_run_age_ms` gauge for the current active run
- `feature126_heartbeat_age_ms` gauge
- `feature126_lease_acquisitions_total` by `owned`, `recovered`, or `contended`
- `feature126_lease_renewals_total` and `feature126_lease_losses_total`
- `feature126_endpoint_attempts_total` by endpoint and result
- `feature126_failure_code_total` by canonical failure code
- `feature126_handoff_total` by status
- `feature126_eligible_companies` and terminal company counters
- `feature126_telemetry_export_failures_total`
- `feature126_readiness` and `feature126_health` gauges

Metrics are supplementary. Durable run evidence is the audit source for exact per-run counts.

### 3.2 Alerts

At minimum, configure these alerts:

- **Worker not ready:** enabled worker readiness is false for the startup grace period.
- **Heartbeat missing:** active run heartbeat age exceeds the heartbeat timeout.
- **Durable evidence unavailable:** telemetry export/acknowledgement fails or its queue remains
  backlogged beyond the allowed threshold.
- **Run stuck:** `Running` or `Handoff` exceeds the configured overall deadline.
- **Daily run missing:** no terminal run exists for the current Tehran date by the operational
  deadline.
- **Run failure:** a terminal `Failed`, `Timeout`, `LeaseLost`, or `HandoffFailed` occurs; page on
  repeated or consecutive occurrences.
- **Partial success:** alert or ticket when the partial-failure count exceeds the agreed tolerance.
- **Lease contention/ownership conflict:** repeated contention, fencing loss, or activation guard
  rejection indicates unsafe deployment configuration.
- **Endpoint degradation:** sustained increases in `RateLimited`, `RemoteServerFailure`, `Timeout`,
  `NoData`, or `InvalidPayload` by endpoint.

Alerts must link to the durable run view and dashboard, and must include the run id, Tehran date,
deployment id, configuration revision, lifecycle state, outcome, and handoff status as event fields
rather than high-cardinality metric labels.

### 3.3 Dashboards and signals

Provide one Feature 126 production dashboard with:

- readiness, health, heartbeat age, telemetry exporter health, and current lease state;
- current Tehran-day run timeline from `Started` through `Handoff` and terminal state;
- success/partial/failure/timeout/lease-loss rates and duration percentiles;
- endpoint attempts/success/failure rates for P/S, P/E, and equilibrium;
- top canonical failure codes and their counts;
- eligible versus terminal company progress;
- handoff success/failure and Feature 125 rejection signals; and
- deployment/configuration revision annotations for rollout correlation.

The dashboard must support drill-down from an alert to one durable run record without requiring the
worker process that created it to still be alive.

## 4. Database impact

Existing tables can be reused:

- `IndustryRelativeValuationSourceLeases` remains the durable lease, fencing, heartbeat timestamp,
  lifecycle envelope, and same-day terminal-marker boundary. Its existing `Owner`, `ExpiresAtUtc`,
  and `UpdatedAtUtc` columns continue to carry the bounded recovery state.
- `IndustryRelativeValuationSourceFacts` remains the immutable provider-scoped ingestion evidence;
  it is not repurposed as a run log.
- Existing Feature 125, Feature 114, and `NoavaranEligibleCompanies` persistence remains
  unchanged.

No database migration is required for this remediation. Do not add a run-history table, column,
index, or migration. The full `FailureCodeCounts`, `EndpointCounts`, deployment/configuration
identity, and lifecycle event history are durable in the external operational evidence sink; the
lease row stores only the bounded state required for fencing and restart recovery. This preserves
the approved schema-free Feature 126 design.

## 5. Preserved boundaries

- **Feature 126:** ingestion observability only—run evidence, worker health/readiness, heartbeat,
  provider/ingestion metrics, and handoff status. It performs no calculation, publication, or watch
  logic.
- **Feature 125:** calculation, publication, ranking, freshness/readiness interpretation, and watch
  behavior remain unchanged. Its existing handoff validation remains the authority for accepting a
  Feature 126 handoff.
- **Feature 114:** visualization contracts and reads remain unchanged. Feature 114 does not regain
  ingestion ownership because of this observability remediation.
- No manual Feature 126 trigger, AI-path provider call, provider payload logging, or new downstream
  side effect is introduced.

## Implementation review acceptance

The blocker is remediated when implementation review can verify that:

1. A run remains queryable after worker restart or crash, including identity, deployment/configuration
   revision, lifecycle/outcome, failure and endpoint counts, handoff status, and timestamps.
2. An expired running lease produces explicit recovery evidence and cannot be mistaken for success.
3. Readiness, health, and heartbeat are externally consumable and distinguish disabled, unavailable,
   stuck, failed, and healthy states.
4. Metrics and alerts are low-cardinality, actionable, and linked to the durable run record.
5. PostgreSQL schema and migrations are unchanged.
6. Feature 125 calculation/publication/watch and Feature 114 visualization behavior are unchanged.
