# Feature 144 banking extension — technical design

Status: approved (2026-10-24). Read [specification](spec.md) and [evidence](research.md) first. This design introduces one industry selection and one bank row/series definition inside the existing Feature 144 path. The supplied JSON is optional reconciliation evidence and creates no runtime or physical-fixture dependency.

## Request and classification

Keep the V2 quarterly-table route and `QuarterlyFinancialReportsQueryUseCase`. Resolve the canonical `NoavaranCurrentApi` company as now. Add a narrow classification reader that projects `Id`, `ProviderName`, `ExternalCompanyId`, and nullable `GroupId` from `NoavaranEligibleCompanies` for the resolved company. Require exactly one eligible row whose provider, canonical ID, and external ID agree. This is one justified view query; it avoids changing the general resolver and proves view eligibility. Name the approved GUID once, for example `BankingIndustryGroupId`, in the template selector. A matching non-null group selects `BankingIncomeStatement`; a known different non-null group selects the existing `GeneralIncomeStatement`. Null, duplicate, missing, or contradictory view evidence returns a typed classification-unavailable outcome. Never infer from names or hardcoded company IDs.

The query result should carry a stable template ID (and classification group/provenance when available) through API serialization and conversation persistence. A fresh query rereads the view, so a catalog group change changes its new template; replay uses the saved template/result snapshot. Audit existing response caches before introducing one; any added cache must include group/version and invalidate on company classification changes. The current path does not need a new database field or migration.

## Source retrieval and normalization

`EfCoreFinancialStatementTableRepository` continues to fetch persisted `NoavaranCurrentApi` `IncomeStatement` headers and source line items. Extend its selected item-ID set by the **approved** banking source IDs and required EPS supplements. Scope is forced to `IsComposing=false` before ranking; legacy source-scope metadata remains checked. Keep bounded predecessor and future comparable-share reference retrieval. Do not call Noavaran at query time, change acquisition/synchronization, add a JSON ingestion path, create a bank repository, or add a new worker/schema.

The banking definition projects **exactly 22 rows** and retains the previous exclusions of the four nonmandatory rows. It adds stable row `source_194` for the direct cumulative source item and `banking_operating_income` for the formula row immediately after it. Item 194 uses the existing adjacent-YTD normalization, persisted catalog identity, and selected report provenance. The formula row has null `SourceItemId`, policy `DerivedBankingOperatingIncome`, and adds standalone cells in the order 306 + 307 + 194 + 61 + 27. It is unavailable if any operand is absent, null, incompatible, or unverified; zero is valid and negative values remain signed. Its typed cell preserves the five operand values, contributing report IDs and line-item IDs, formula policy, and `million_rial` unit. The existing two margin rows remain the only yellow rows. This registration is banking-only; the General template, its row definitions, calculations and rendering stay unchanged. The two derived margin rows also retain null `SourceItemId`; source-catalog validation for direct rows remains strict.

For direct flows Q1=3M, Q2=6M−3M, Q3=9M−6M, Q4=12M−9M, with the same fiscal-year, provider, separate scope, source-item, unit/scale, and compatible period checks as Feature 144. The bank rows use signed decimal source amounts. Do not force an expense sign. Item 153 remains point-in-time; the newest quarter in the selected table window supplies the common displayed share basis for every quarter. Comparable EPS uses existing row-143 net profit (313 fallback only on missing/null 143) and this same verified item-153 basis, rounding and provenance. Do not change EPS to source item 160 or subtract cumulative EPS.

After standalone normalization, compute:

* `banking_gross_margin = quarter(source_306) / quarter(source_304) × 100`
* `fee_profit_margin = quarter(source_307) / quarter(source_26) × 100`

Use the existing typed percentage-cell pattern, but make it operand-driven so the exact same safety checks and report/line IDs propagate. Reject absent, incompatible, or zero denominators. The stored unit is `percent` and the value has already been scaled by 100. Renderer, web, PNG, QoQ, and chart must never rescale it. For comparison, preserve an exact percentage-point delta separately from relative `%` change. Use `row.Policy` or a derived-kind field instead of checking only literal `gross_margin`.

The source catalog supports direct banking item 194 with source title `خالص سایر درآمدهای غیر مشاع`; its approved table label is `سایر درآمدها و هزینه‌های عملیاتی`. Item 61 retains the source's non-operating qualifier in provenance. Item 13 is the selected tax source; item 336 is a crosscheck, never an added tax amount or silent fallback. The six reports show `13=336`, `306=304+305`, `307=26+7`, and `140=199+200`. The latter equality is not used to calculate operating income. Items 140 and 199 are not substitutes for the approved five-input formula; item 309 is not a substitute for item 194; no depreciation row or `143 − 278` calculation is added. The earlier exclusions for discontinued-operation income and the other previously omitted rows remain in force. See the [matrix](research.md#reconciliation-matrix). Persistence validation should compare selected report IDs/titles/units when Development access is available; JSON is never a runtime requirement.

## Typed result, text, and presentation

Keep one `QuarterlyFinancialReportTableResult` for both templates, adding the template discriminator. Its rows/cells already provide decimal values, unit, source IDs, selected report metadata, zero/null distinction, and provenance. `FinancialStatementTableQueryUseCase.RenderQuarterly` should render either row definition from the typed result, including the two percentage rows at one decimal in Persian digits. The four excluded rows never appear in typed rows, Markdown, web, PNG, or replay. V2 workflow, API DTO, assistant message persistence, and replay pass the typed result unchanged, with version-safe behavior for older general-template messages.

For banking, wire the existing typed quarterly result from the AI response and replay into `QuarterlyFinancialTableModel` with stable row IDs, numeric nullable cell values, units, states and template ID. Render text/HTML from that model. Keep the legacy parser and accept historical 20-row banking snapshots as-is; no frontend rule may assume either 20 or 22 rows when reading saved results. Do not infer bank mappings from display position or Persian labels. The browser chart and PNG exporter both consume the same typed model; the two new rows are table-only. This is a targeted client adapter, not another financial pipeline.

The table retains the existing RTL fixed-width structure, Persian fiscal/period-end labels, teal header, pale labels, negative parentheses, zero dash, and newest quarter to the left. Apply full-row yellow styling and bold type to **both** bank margin rows in web and canvas export. At mobile width, use existing compact font and fixed column proportions; verify no document-width overflow. For bank rows, define favorability by explicit row semantics (expenses include 305, 7, 5, 6, 12 and the selected tax mapping when approved), not by raw negative sign. Unknown or mixed-sign meanings use neutral coloring. Leave the current non-bank `EXPENSE_SOURCE_ITEM_IDS` behavior unchanged. QoQ display must distinguish relative change from percentage-point change.

## Chart

Reuse the existing Recharts `ComposedChart` and canvas exporter. The final approved Banking chart is exactly **3 BAR + 2 LINE = 5 SERIES**: three bars (`source_304` for درآمد تسهیلات و سپرده‌گذاری, `source_306` for خالص درآمد تسهیلات و سپرده‌گذاری, and `source_143` for سود خالص) on the `million_rial` axis; and two lines (`banking_gross_margin` = standalone(306) / standalone(304) × 100, and `fee_profit_margin` = standalone(307) / standalone(26) × 100) on the `percent` axis. `source_305` remains a table row and is excluded from chart series. Bind series by stable row IDs and typed decimals, never display text. Use separate Y axes and clear units, Persian numeral formatters and fiscal-quarter labels, a consistent legend/palette, and `connectNulls=false`. Each monetary bar plots its signed value around zero; missing values are null gaps. Do not stack. Use the same selected five periods, oldest to newest on the chart's LTR x-axis. The RTL table remains separate. The canvas exporter needs the corresponding three-bar/two-line drawing and secondary axis labels; avoid duplicating financial calculations in canvas code.

Banking chart visibility is mandatory and included in bank PNG even when `QuarterlyFinancialTable:ShowChart=false`; preserve that configuration's existing effect on non-bank charts. The existing `CHART_HEIGHT` may be adjusted only if five-series legend/axis labels need space. Browser and PNG output must be checked at desktop and mobile widths. No Feature 144 server-side or Telegram chart exporter was found; Feature 143 Telegram ingestion is untouched.
