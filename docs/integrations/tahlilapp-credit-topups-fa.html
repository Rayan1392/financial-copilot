راهنمای فنی یکپارچه‌سازی خرید اعتبار از ساپیو

این سند قرارداد سروربه‌سرور برای ثبت خرید اعتبار و استعلام موجودی را شرح می‌دهد. این راهنما فقط شامل endpointهای اعتبار است.

۲. شناسه کاربر

userId باید دقیقاً شناسه پایدار کاربر، سمت همکار باشد؛ این مقدار با شناسه داخلی کاربر ساپیو متفاوت است. ساپیو این مقدار را از پیوند هویت همکار پیدا می‌کند و اشتراک را از رکوردهای همگام‌شده خودش بررسی می‌کند. نام، شماره تلفن یا ایمیل را به‌جای آن ارسال نکنید.

۳. افزایش اعتبار با POST

بدنه باید دقیقاً چهار فیلد زیر را داشته باشد. فیلد اضافه یا فیلد جاافتاده پذیرفته نمی‌شود.

{
  "invoiceId": "TA-INV-2026-000123",
  "userId": "<شناسه پایدار کاربر سمت همکار>",
  "creditsPurchased": 100,
  "paidAtUtc": "2026-11-03T12:30:00Z"
}
  • invoiceId: شناسه یکتای فاکتور/خرید در سامانه همکار؛ حداکثر ۱۶۰ نویسه و بدون فاصله ابتدا یا انتها.
  • userId: شناسه پایدار کاربر سمت همکار؛ حداکثر ۱۲۸ نویسه و بدون فاصله ابتدا یا انتها.
  • creditsPurchased: تعداد اعتبار مطابق بسته فعال سمت ساپیو. بسته‌های seed‌شده فعلی ۱۰۰، ۵۰۰ و ۱۰۰۰ اعتبار هستند؛ بسته فعال محیط مقصد ملاک نهایی است.
  • paidAtUtc: زمان واقعی پرداخت به UTC در قالب ISO 8601، همراه با Z یا offset صریح. مقدار نباید در آینده باشد.

نمونه پاسخ موفق با HTTP 200:

{
  "status": "granted",
  "invoiceId": "TA-INV-2026-000123",
  "grantId": "b0d1e5ea-4cd2-43ed-9e34-9e1ddc4d70b8",
  "creditsGranted": 100,
  "expiresAtUtc": "2026-11-30T18:03:27+00:00",
  "grantedAtUtc": "2026-11-03T12:31:04.1234567+00:00"
}

Idempotency و retry

برای retry شبکه، همان invoiceId و همان چهار مقدار را دوباره بفرستید؛ پاسخ همان رسید و grantId قبلی را برمی‌گرداند و اعتبار دوباره اضافه نمی‌شود. برای درخواست جدید، invoiceId تازه بسازید. استفاده مجدد از یک invoice با body متفاوت خطای topup-identity-conflict می‌دهد.

هر POST باید JWT تازه با jti تازه داشته باشد؛ حتی در retry. jti در سطح صادرکننده یک‌بارمصرف است.

۴. استعلام موجودی

این endpoint فقط وضعیت محلی ثبت‌شده را می‌خواند، داده را تغییر نمی‌دهد و به‌صورت عمومی قابل فراخوانی است. در پاسخ availableCredits موجودی قابل‌مصرف را نشان می‌دهد، پس رزروشده‌ها از آن کم شده‌اند.

۵. JWT شریک

برای POST هدر زیر الزامی است:

Authorization: Bearer <JWT>
Content-Type: application/json

مقادیر قرارداد JWT باید دقیقاً مطابق جدول زیر باشند:

مقدارالزام
iss / تنظیم API یعنی Issuertahlilapp-topup
aud / تنظیم API یعنی Audiencesapio-tahlilapp-topup
scopetopup.deliver
jtiرشته یکتا، حداقل ۱۶ و حداکثر ۲۰۰ نویسه؛ برای هر POST تازه
expانقضای JWT به Unix time ثانیه؛ الزامی و باید معتبر باشد
kid در headerشناسه کلیدی که با یکی از نام‌های عضو SigningKeys برابر باشد
alg در headerHS256
subدر پیاده‌سازی فعلی برای این endpoint اجباری نیست؛ برای شناسایی صادرکننده توصیه می‌شود.

برای سازگاری ساده، عمر توکن را حدود ۵ دقیقه بگذارید. API برای اعتبارسنجی زمان ۳۰ ثانیه clock skew دارد. توکن بدون امضا، امضای نامعتبر، kid ناشناخته یا jti تکراری پذیرفته نمی‌شود.

تنظیم API و مدیریت کلید

در محیط API، endpoint باید با Billing:TahlilAppTopUps:Enabled=true فعال شود. مقادیر احراز هویت مورد انتظار:

{
  "Billing": {
    "TahlilAppTopUps": {
      "Enabled": true,
      "Authentication": {
        "Issuer": "tahlilapp-topup",
        "Audience": "sapio-tahlilapp-topup",
        "SigningKeys": {
          "<KID اعلام‌شده در فایل امن>": "<secret اعلام‌شده در فایل امن>"
        }
      }
    }
  }
}

در JWT ارسالی، مقدار claim یعنی "iss": "tahlilapp-topup" باید با Issuer برابر باشد. مقدار claim یعنی "aud": "sapio-tahlilapp-topup" باید با Audience برابر باشد.

محرمانگی کلید: مقدار واقعی SigningKeys داخل این سند نیست. مقدار و KID مربوط به آن در فایلی جداگانه و از مسیر امن برای تیم فنی همکار ارسال خواهد شد. کلید را در سورس، Postman collection مشترک، log یا تیکت قرار ندهید. برنامه شریک باید از secret store بخواند و مقدار کلید را در log چاپ نکند.

نمونه‌های چندزبانه برای ساخت JWT و ارسال درخواست

در تب‌ها نمونهٔ ساخت JWT با C#، PHP، Python و Node.js و نمونهٔ ارسال درخواست با curl آمده است. مقدار SigningKey و kid را از secret store یا فایل امن دریافت کنید؛ کلید را در کد ثابت ننویسید. در نمونه‌های curl، متغیر TOPUP_JWT باید از برنامهٔ شما پر شود؛ curl به‌تنهایی JWT امضا نمی‌کند.

پکیج موردنیاز: System.IdentityModel.Tokens.Jwt.

using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;

static string CreateTopUpJwt(
    string issuer, string audience, string keyId, string signingKey)
{
    var now = DateTime.UtcNow;
    var claims = new[]
    {
        new Claim("sub", "partner-topup"),
        new Claim("scope", "topup.deliver"),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString("N"))
    };

    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(signingKey));
    var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    var jwt = new JwtSecurityToken(
        issuer: issuer,             // "tahlilapp-topup"
        audience: audience,         // "sapio-tahlilapp-topup"
        claims: claims,
        notBefore: now.AddSeconds(-5),
        expires: now.AddMinutes(5),
        signingCredentials: credentials);
    jwt.Header["kid"] = keyId;      // همان KID نگاشت‌شده در SigningKeys
    return new JwtSecurityTokenHandler().WriteToken(jwt);
}

با PHP و توابع داخلی؛ کلید به‌صورت متن UTF-8 از متغیر محیطی خوانده می‌شود.

<?php
function b64url(string $value): string {
    return rtrim(strtr(base64_encode($value), '+/', '-_'), '=');
}

$issuer = 'tahlilapp-topup';
$audience = 'sapio-tahlilapp-topup';
$kid = getenv('TOPUP_KID');
$key = getenv('TOPUP_SIGNING_KEY'); // از secret store؛ هرگز log نکنید
if (!$kid || !$key) throw new RuntimeException('Missing signing credentials');

$now = time();
$header = ['alg' => 'HS256', 'typ' => 'JWT', 'kid' => $kid];
$payload = [
    'iss' => $issuer,
    'sub' => 'partner-topup',
    'aud' => $audience,
    'scope' => 'topup.deliver',
    'iat' => $now,
    'exp' => $now + 300,
    'jti' => bin2hex(random_bytes(16)),
];
$unsigned = b64url(json_encode($header, JSON_UNESCAPED_SLASHES | JSON_THROW_ON_ERROR)) . '.' .
            b64url(json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_THROW_ON_ERROR));
$signature = hash_hmac('sha256', $unsigned, $key, true);
$jwt = $unsigned . '.' . b64url($signature);

// هر POST و retry باید JWT تازه با jti جدید داشته باشد.
echo $jwt;

فقط با کتابخانه‌های استاندارد Python؛ کلید از محیط خوانده می‌شود.

import base64, hashlib, hmac, json, os, secrets, time

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b'=').decode('ascii')

issuer = 'tahlilapp-topup'
audience = 'sapio-tahlilapp-topup'
kid = os.environ['TOPUP_KID']
key = os.environ['TOPUP_SIGNING_KEY'].encode('utf-8')
now = int(time.time())
header = {'alg': 'HS256', 'typ': 'JWT', 'kid': kid}
payload = {
    'iss': issuer, 'sub': 'partner-topup', 'aud': audience,
    'scope': 'topup.deliver', 'iat': now, 'exp': now + 300,
    'jti': secrets.token_hex(16),
}
unsigned = (b64url(json.dumps(header, separators=(',', ':')).encode()) + '.' +
            b64url(json.dumps(payload, separators=(',', ':')).encode()))

print(unsigned + '.' + b64url(signature))  # secret را چاپ نکنید

با Node.js و ماژول داخلی crypto.

const crypto = require('node:crypto');

const b64url = value => Buffer.from(value).toString('base64url');
const now = Math.floor(Date.now() / 1000);
const header = {
  alg: 'HS256', typ: 'JWT', kid: process.env.TOPUP_KID
};
const payload = {
  iss: 'tahlilapp-topup', sub: 'partner-topup',
  aud: 'sapio-tahlilapp-topup', scope: 'topup.deliver',
  iat: now, exp: now + 300,
  jti: crypto.randomBytes(16).toString('hex')
};
const unsigned = `${b64url(JSON.stringify(header))}.${b64url(JSON.stringify(payload))}`;
const signature = crypto.createHmac('sha256', process.env.TOPUP_SIGNING_KEY)
  .update(unsigned, 'ascii').digest();
const jwt = `${unsigned}.${b64url(signature)}`;
process.stdout.write(jwt); // خود کلید را چاپ یا log نکنید

مقادیر iss، aud و scope باید دقیقاً مطابق تنظیمات اعلام‌شده باشند. کلید سمت API با UTF-8 به کلید HMAC تبدیل می‌شود؛ سمت صادرکننده نیز باید دقیقاً همان متن کلید را با UTF-8 به کار ببرد. اگر کلید در فایل امن به شکل متن Base64 ارائه شد، آن را خودسرانه decode نکنید؛ طبق قالب اعلام‌شده برای همان کلید عمل کنید.

۶. نمونه‌های چندزبانه برای POST و استعلام

نمونه‌های زیر هر دو endpoint را فراخوانی می‌کنند. برای POST، JWT را در همان برنامه با روش بخش قبل بسازید و در هدر Bearer بفرستید؛ استعلام موجودی به JWT نیاز ندارد. مقادیر invoice، شناسه کاربر، تعداد اعتبار و زمان پرداخت باید از پرداخت تأییدشده بیایند.

فرض شده متد CreateTopUpJwt از نمونهٔ C# بخش قبل در دسترس است.

    HttpMethod.Post, $"{baseUrl}/api/v1/billing/partners/tahlilapp/top-ups");

در پاسخ POST، در صورت موفقیت status برابر granted است؛ پاسخ GET شامل طرح، بازهٔ اشتراک، quotaMode و موجودی قابل‌مصرف است. برای retry، بدنه و invoice را عیناً تکرار کنید ولی JWT تازه با jti تازه بسازید.

۷. قواعد اشتراک و انقضای اعتبار

  • خرید اعتبار فقط برای کاربری قابل grant است که اشتراک فعال Plus یا Pro داشته باشد. کاربر Free و Max امکان دریافت اعتبار اضافه از این endpoint را ندارد.
  • اشتراک باید در زمان paidAtUtc فعال بوده باشد: شروع بازه شامل است (startsAtUtc <= paidAtUtc) و پایان بازه شامل نیست (paidAtUtc < expiresAtUtc).
  • اشتراک و هویت باید در داده‌های authoritative ساپیو همگام باشند. پاسخ مثبت سرویس تحلیل‌اپ به‌تنهایی جایگزین رکورد محلی اشتراک نیست.
  • اعتبار خریداری‌شده تا پایان همان بازه اشتراک Plus/Pro قابل‌استفاده است. مقدار استفاده‌نشده با پایان اشتراک منقضی می‌شود و به دوره یا اشتراک بعدی منتقل نخواهد شد.

۸. خطاها و پاسخ‌ها

خطاهای endpointها در قالب Problem Details و با فیلدهای type، title، status، code و correlationId برمی‌گردند. مقدار correlationId را برای پیگیری خطا نگه دارید؛ توکن یا secret را در گزارش خطا قرار ندهید.

چک‌لیست ارسال POST: چهار فیلد دقیق؛ بسته فعال؛ شناسه پایدار کاربر سمت همکار؛ پرداخت UTC معتبر؛ Plus/Pro فعال در زمان پرداخت و منقضی‌نشده هنگام تحویل؛ JWT امضاشده با Issuer، Audience، scope، KID، exp و jti معتبر؛ invoice یکتا؛ jti تازه برای هر درخواست.

مبنای مستندات: قرارداد endpoint و سرویس فعلی top-up شریک در API ساپیو. مقدار secret و KID اختصاصی هر شریک خارج از این سند و از مسیر امن تحویل می‌شوند.
