# Feature 152 — TahlilApp Max subscription

**Status:** local implementation and focused verification complete; external/staging readiness remains pending. Linked to [Feature 139's authoritative plan contract](../139-tahlilapp-session-exchange/TahlilAppIntegrationContract.md) and shared lifecycle tasks T-40–T-43. Separate from [Feature 151 top-ups](../151-tahlilapp-paid-credit-top-ups/spec.md), whose partner delivery remains disabled. **Max** is the confirmed customer-facing name and `sapio_max` is its approved TahlilApp slug. Max uses exactly the Pro capability matrix and has Unlimited quota through TahlilApp's authoritative expiry. While Max is active it controls quota mode; after Max expires, the latest-expiring active non-Max window determines the effective plan. Finite grants remain independent and expire at their own source dates. TahlilApp supplies expiration; SapioAI never computes it from the current 90-day commercial term.

## Verified compatibility review

- **External mapping:** `TahlilAppOptions.PlanMap`, exchange parsing, status parsing, and API defaults map `sapio_max` to canonical `Max`. The configured parser path preserves TahlilApp's supplied `starts_at`/`expires_at`; local tests cover the approved slug and authoritative expiry. The external TahlilApp checkout and staging response have not been verified in this repository.
- **Plan and capabilities:** `BillingEntityConfigurations` seeds Max as `QuotaMode=Unlimited` and `IncludedCredits=0`, with an explicit Max capability matrix exactly matching Pro, including each capability limit. The migration persists these rows for existing databases. No Pro inheritance is used. `PlanCapabilityService` checks enabled rows and active windows, including revocation. Unlimited never creates a numeric wallet grant, reservation, or debit.
- **Admission and accounting:** `AiFacadeBillingHook.TryReserveAsync` and `GetReservationCreditsAsync` enforce numeric sufficiency, then `UsageReservationAuthorizationService.ReserveAsync` checks wallet capacity, writes a numeric reservation and increases `ReservedAmount`. `EnsureReservedCapacityAsync` may increase it. `UsageFinalizationService.CommitAsync` debits wallet and writes a charge ledger entry; `ReleaseAsync` frees the hold. `UsageRefundService.RefundAsync` adds credits to the wallet. `UsageReservationRow` has no quota mode or source subscription ID, and `UsageReservation` rejects `reservedCredits <= 0`, so its domain invariant must become mode-aware. These are concrete change points; a display-only Unlimited flag would still fail at zero balance or create false debits.
- **Reads/UI:** `UsageController.GetMyUsage` returns numeric balance/reserved/available/included credits; `src/frontend/src/lib/market-view.functions.ts`, `src/frontend/src/lib/credit-progress.ts` and `src/frontend/src/components/app/sidebar.tsx` assume finite credit progress. Admin numeric credit history and reports must continue to show actual finite wallet/ledger numbers.

## Shared lifecycle dependency and entitlement model

Feature 139 T-40–T-43 owns this prerequisite for both features: Free receives **250 credits once per user**, valid only until its assigned expiration; Plus receives **260 total** and Pro **2600 total** per entire authoritative paid window. No monthly allocation, refill or reset. A genuine paid renewal creates one new keyed full-window grant; exhausted/expired Free never refills, including after paid expiry or cooldown. Historical 25-credit Free grants count as already received and do not trigger an automatic 225-credit supplement. Existing wallet/source rows need conservative reconciliation. Feature 152 does not duplicate that implementation. TahlilApp commercial prices are Plus 1,000,000, Pro 5,000,000 and Max 25,000,000 TOMAN per 90 days; these do not enter SapioAI's top-up webhook or determine entitlement dates.

Add canonical `Max` subscription plan with explicit `CreditQuotaMode = Finite | Unlimited` (or equivalent enum) on plan/entitlement projections. `IncludedCredits` may remain numeric zero for schema compatibility **only alongside the explicit mode**; zero does not mean unlimited. Wallet `Balance`, `ReservedAmount`, ledger numeric credits, reports and estimates remain finite numbers. No `-1`, huge grant, repeated grant or ambiguous null. Feature 139's official `subscription.plans[]` still carries `slug`, `starts_at`, `expires_at`; map the approved Max slug `sapio_max` through the configurable parser/map/validator and persist an `ExternalPlanSubscriptionRow`. No new upstream date or hardcoded duration is required. While any active, unrevoked Max window exists, Max is the effective Unlimited entitlement, even when a finite plan window expires later; its expiry is the latest active Max window expiry. After Max expires, select the non-Max plan from the active window with the latest authoritative expiry. Preserve the existing Pro-over-Plus choice only for an exact expiry tie. If no paid window remains, use finite Free access **without a new Free grant** and subject to existing paid-expiry cooldown. Include Max in last-paid-expiry/cooldown/revocation logic. Renewal is a new authoritative window; no unrelated finite balance is reset, and expired finite/top-up sources do not revive.

**Overlapping windows:** Active Max controls quota mode and authorizes Unlimited usage without consuming finite credits, even if another paid window has a later expiry. Max remains valid only until its own authoritative expiry. Once Max expires, recompute from remaining active non-Max windows and choose the latest-expiring one. For an exact non-Max expiry tie, retain the already-defined Pro-over-Plus choice; no new tie-break is added. Finite allowance grants and eligible top-ups from all active sources are summed for finite spendable balance, but remain linked to and expire with their own source. A longer subscription never extends, transfers, or carries over a shorter source's credits. Existing accounting history is preserved; future Plus-to-Pro transfers are not performed. Feature 139's Free-credit forfeiture and paid-expiry cooldown policy apply to Max as a paid plan, but cooldown completion never creates a second Free grant.

## Request lifecycle

At admission, enforce authentication, account enabled state, explicit operation capability/limits and existing operational/rate controls. Revalidate entitlement as currently done. If any active Max window exists, Max controls quota mode: bypass numeric wallet sufficiency and create an idempotent reservation with `BillingQuotaMode=Unlimited`, source `ExternalPlanSubscriptionRow.Id` for a live Max window, `ReservedCredits=0`, and no wallet hold. Use the latest-expiring active Max source for this attribution. A zero-credit reservation is valid **only** with explicit Unlimited mode/source. Store mode/source immutably in the reservation and carry them through `BillingReservationHandle` and charge ledger metadata. Duplicate request keys must compare mode and source as well as account/operation/fingerprint; never reinterpret a replay using the current plan. After Max expires, recompute the latest-expiring active non-Max plan and use finite admission. Finite admission includes all spendable allowance and top-up sources and holds by earliest source expiry. Read-side spendable finite balance excludes expired sources even when cleanup is late (Feature 139 T-42).

An Unlimited capacity upgrade is a no-op for wallet holds but still records the execution-cost estimate. On completion, record actual token usage and available provider-reported or estimated cost, operation, outcome and correlation as now, with `CreditsCharged=0`, `BillingQuotaMode=Unlimited`, and original source window; do not debit wallet or create a fictitious credit grant. Commit reservation and zero-credit usage entry atomically and idempotently. Cancellation, failure or timeout releases/finishes the reservation without a wallet change; retry returns the original result. A positive-credit usage-refund request for an Unlimited zero-credit charge is rejected as invalid; no refund ledger credit or wallet increment occurs. The original zero-credit usage audit remains. Existing finite usage refunds remain finite and source-aware.

**Crossing a boundary:** natural expiry or a different plan after an admitted request does not reprice/reclassify that reservation. It may finalize under its original Unlimited mode with zero debit even after `expires_at`, subject to the existing reservation lifetime; new admissions after Max expiry use the latest-expiring remaining non-Max plan. Revocation follows Feature 139's current release-pending-reservations behavior: release pending reservations affected by the revoked source, reject late finalization of those released reservations, and retain committed usage audit. A finite reservation admitted before Max became active keeps its finite holds and source expiries. Unheld credits expire at their own source boundary even while another plan remains active. Replay of a committed request remains idempotent across plan changes.

## API and presentation

Extend `GET /api/v1/usage/me` and equivalent user/admin subscription summaries with `creditQuotaMode: "Finite" | "Unlimited"` and authoritative `subscriptionExpiresAtUtc` for the **currently effective window**. Keep `balance`, `reservedCredits`, `availableSpendingCapacity`, `planIncludedCredits` numeric/finite or documented nullable where already allowed; they describe finite wallet state, **not** Max spending capacity. Add quota mode/source to usage metadata and internal ledger/report projections so zero-credit Max operations are distinguishable from free/failed finite operations. Existing numeric report totals remain numeric. Frontend shows **«نامحدود»** with the expiry and hides finite progress for active Max; it never sends `∞` as a numeric value. On expiry/revocation it reverts to the effective finite/Free display immediately after refreshed entitlement, without waiting for cleanup.

The Feature 151 partner balance read (`GET /api/v1/billing/partners/tahlilapp/credit-balance`) applies this same overlap policy and reports the same effective plan and expiry. It is a separate partner contract and uses `quotaMode: "finite" | "unlimited"` with `availableCredits: null` only when `quotaMode` is `unlimited`. That null is never ambiguous because the explicit mode always accompanies it. See [Feature 151's integration contract](../151-tahlilapp-paid-credit-top-ups/integration-contract.md).
