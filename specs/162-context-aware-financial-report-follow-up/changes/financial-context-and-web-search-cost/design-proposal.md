# Financial Context and Web Search Cost Optimization

Status: Proposed — not approved

Applies to Features 162 and 163 on the V2 path. Phase A reduces the cost of sending the same financial evidence. Phase B improves the external evidence obtained per search. The implementation sequence below is for Gate A review. The detailed implementation plan and Gate B follow explicit design approval.

## 1. Current financial context

- Feature 162 resolves the active displayed report from the conversation and projects its structured payload. With Grounded Analysis enabled, it first makes a lightweight disposition call with the company, report type, periods, distinct item labels, bounded recent history and question. The call has its own strict schema and no web tool. A hand-back exits before loading supporting data or invoking Sol. An answered disposition leads to the analysis prompt, which again includes the question and recent history. The disposition sends labels and period names again on a separate call, but sends no financial values. Feature 163 starts from a verified single-symbol fallback offer. Only after explicit confirmation does it resolve the offer, read the company's quarterly income statement and build the analysis request for the original question. No conversation history is added to that analysis prompt.
- Both analysis builders use `CompanyAnalysisDataPackLoader` and `CompanyDataPrompt.Fit`. The primary report is reused. Supporting income statement, balance sheet, cash flow and monthly sales totals use the same statement or trend use cases as chat. Reads are sequential, same-company, and bounded by a three-second per-section and eight-second total timeout in the checked-in configuration. Cash flow respects its capability flag. Missing, disabled, timed-out and other unavailable sections carry explicit reasons. Provider and report selection remain with the existing query use cases.
- `ReportDataSetBuilder` projects available quarterly cells and deterministic QoQ growth or percentage-point changes, margins and cost ratios, plus same-fiscal-quarter YoY growth where both inputs exist. The normal quarterly query asks for five quarters and explicit quarterly requests can reach twelve. Balance sheet uses report snapshots, ratios and the selected comparison baseline. Cash flow carries usable cells and KPIs, including the existing caveat on unverified values. The monthly section carries the trend points as well as the latest, previous and same-month-prior-year amounts, average, fiscal YTD and available percentage comparisons. Some monthly summary values can also appear as trend points. Their roles and period semantics differ, so equal values alone are insufficient to establish equivalence.
- The shared renderer applies display units and formats values with up to two decimals. Each section has a type, scope, primary marker where applicable, and a local newest-first period legend. Income scope derives from the report's consolidation flag, balance sheet is company-only, and cash flow carries its reported basis label. Keys such as `P0` are local to each section and do not imply alignment across fiscal quarters, statement dates and months. Each fact row contains ID, label, period key, value and unit. Each calculation row adds a formula and operand IDs, with matching period names in formulas replaced by period keys when available. IDs are renumbered across the fitted pack and retained in the in-memory union the validator receives.
- Fitting starts with all periods. It then tries two newest periods per supporting statement and twelve months of monthly activity, then shortens 162 history to two messages, then drops supporting sections in cash flow, balance sheet, monthly activity and income statement order, then shortens the primary report oldest-first. In checked-in profiles, the targets are 24,000 estimated input tokens for Simple and 40,000 for Deep, with a 120,000 ceiling. The builders estimate system and user messages at 2.5 characters per token. Schema, provider framing and retrieved web content are outside that estimate. Legacy single-report paths have their own 5,000-token targets and renderer.
- The full populated historical context contains useful evidence, including YoY bases and monthly seasonality. The strongest candidates for savings are repeated Persian labels and units, the same terms repeated inside growth formulas, and boilerplate repeated across calculation rows. Fact and calculation values are intentionally separate. System rules and the schema repeat some output instructions, and 162 can resend prior report prose as continuity context, capped at six messages and 1,200 estimated tokens. Those are smaller, separately measurable candidates.

A lower budget or a blanket two-period cut could remove the evidence needed to explain earnings quality. Treat any window or fallback-order change as a separate fixture-backed decision. |

Apply compaction only to the shared company-data analysis renderer. Update its prompt legend to explain the data shape without inventing analytical observations. Keep the existing disposition and legacy single-report renderers. Defer monthly summary deduplication and removing data from 162 history until captures show material savings and prove that temporal semantics and reference resolution survive.

**Evidence and grounding.** The analysis models parse `usedEvidenceIds` from the strict reply. The answer handlers do not currently use those IDs to authorize each number. Numeric Grounding checks the answer's numeric magnitudes against the displayed fact/calculation union and allowed numbers from periods, labels, company/question text and server score, with its existing rounding tolerance. It does not establish sign, unit, period, scope or claim-level attribution. Preserve this behavior and the strict schema. Test ID-to-record equivalence for every emitted row, including sign, rendered value, original display unit, real period, scope and operand order. When testing identical fitted states, expect identical IDs. A better-fitting state may retain more evidence and receive different request-local IDs under the current renumbering scheme.

A pre-existing edge case matters for formula compaction. `KeepNewestPeriods` filters by a calculation's target rank, and `Renumber` passes through an unmapped operand ID. A base fact may therefore be missing, and a raw ID can alias a different displayed fact. Only use operand-based shorthand when the operands resolve to their original facts in the same fitted section. Cover trimmed YoY and cross-section ID collisions in fixtures. Preserve the explicit basis/formula where the displayed operands are incomplete and avoid emitting unresolved references as if they resolved. A baseline or origin cannot be inferred from the numeric value alone.

## 3. Current web execution and proposed Phase B

`GroundedAnalysisModelCall` adds the web capability and options only when the selected choice enables it. `OpenAiHostedAiModelTransport` sends one Responses analysis request with the strict JSON schema, effort and output limit, plus `web_search` when enabled. The checked-in settings are `search_context_size=low`, approximate country `IR`, empty domain allowlist, and `max_tool_calls=1` for Simple or `2` for Deep. There is no instruction forcing a tool call at the transport level. The current shared prompt instructs broad Deep reviews to research outside context even if the report contains enough numbers. It lists many possible topics and asks for targeted, non-repeated queries. Simple and narrow questions already have a relevance gate. Company-data rules already forbid searching for report figures, missing report copies and monthly totals. Product-level detail outside the pack remains eligible.

The transport counts every returned `web_search_call` output item. It collects URLs from action results, opened/found page URLs and native citation annotations, then deduplicates exact strings. The reply separately declares `externalSources`. After answer layout normalization, `ExternalEvidenceValidator` accepts referenced `[Wn]` entries whose HTTP(S) URL matches a normalized consulted URL and whose declared date is nonempty. For declared values it requires a matching nearby number in that segment. URL normalization strips tracking parameters and fragments and handles the `www.` prefix and trailing slash. The validator drops an invalid list item or rejects the answer for an invalid takeaway or paragraph. Accepted markers and covered external numbers are removed from the text sent to Numeric Grounding, and the server appends only the validated, cited source list to the visible answer. This confirms provenance and local numeric consistency. Authority, publication-date accuracy, period relevance and faithful interpretation require review.

| Priority | Change | Decision |
|---|---|---|
| 1 | Replace the broad Deep research directive with a material-question rule. Identify one unresolved driver that could change the interpretation, then search using the Persian ticker/company name, fiscal period or event dates and the named driver. Start with relevant Codal or company disclosures. Use the exchange, official regulator or established reporting when it is the relevant publisher or a primary disclosure cannot be found. | Run the first targeted search whenever there is a material question. A second query serves a different evidence gap or reaches a better primary source for the same material claim. Stop when usable evidence is obtained or a refined search offers little prospect of adding value. An empty result leaves a labeled hypothesis or an explicit gap. Maintain the current web-off rules, separation of report facts, external evidence and inference, and the requirement for dated, relevant citations. |
| 2 | Extend existing usage diagnostics to distinguish returned web events, `search`, `open_page`, `find_in_page` and unknown actions. Record the existing consulted-source count and add the final validated cited-source count for the same correlation ID. Keep input, cached input, output, reasoning and latency. | Keep counts and status only in operational telemetry. No query strings, prompt data, response text or URLs in logs. For owner-provided sanitized captures, inspect query repetition and citation relevance offline. Use provider billing data for billable units where available. |
| 3 | Hold the current cap, location, low search context and empty global allowlist in the first comparison. Review a cap reduction only if paired owner runs show surplus paid searches after the prompt change. | A lower cap can block a useful refinement or the source-opening step. Global Codal-only filtering can hide company announcements, regulator directives and relevant industry sources. Current provider documentation describes a returned-token budget, but model-specific behavior with this strict schema and its effect on useful citations remain unverified. Leave it out of the first change. |

The provider documents `max_tool_calls` as a per-response built-in tool bound and describes `search`, `open_page` and `find_in_page` as distinct actions. Search actions incur a tool fee. The historical cap of two and three returned items can coexist in the evidence. The action mix in those runs and the applicable charges still require raw action records and provider usage reconciliation. These figures come from the request. The checked-in [A4 evaluation](../sol-deep-analysis-web-search/evaluation-a4.md) is a separate فولاد baseline with an earlier prompt and data-pack setup. Its new Deep+web runs reported three items per searching run and one final source in five of six runs, from 16–30 consulted pages in cited answers. The cited pages were secondary sources. The 163 new Deep web-off runs used about 8,000 input tokens, while new Deep web-on runs used about 23,500. The difference includes search context and different execution behavior, so it is unsuitable as a precise estimate of either pack size or savings. A4 also found that the more research-oriented prompt introduced useful hypotheses, industry factors and cash-conversion questions. Preserve that analytical depth. The repository records A4 aggregate results and points to raw prompts and JSONL in a separate session scratchpad. The three supplied runs' raw request/response payloads, search action mix, individual cache usage, exact provider charges and final answers were unavailable in the inspected workspace. Source relevance and budget degradation on those runs therefore remain unverified.

**Offline measurement.** A temporary local harness rendered the existing synthetic `LargeQuarterly` fixture through the current renderer with all periods retained. The four-section variant combines it with the repository's small balance-sheet, cash-flow and monthly fixtures. A standalone text prototype grouped consecutive rows by label and unit, then used method aliases only when it could reconstruct the same rendered formula from the two displayed operands in the same section. The counts include the added format legend. They cover only the company-data block, using the repository's character-based estimator, and are neither Sol token counts nor projections for the named executions.

The fixtures are deliberately dense in quarterly comparisons. The four-section cases add only 19 supporting facts and seven supporting calculations, so they are evidence about the encoding, with limited coverage of a large غبهنوش pack. No savings are credited to period trimming, routing/history edits or reduced search-content usage. Those depend on the actual case data and execution.

Use paired replay to measure the system prompt, report sections (facts and calculations separately), history, question, schema and tools. Count the exact serialized text locally with a supported tokenizer if available. Otherwise publish characters and the current `ceil(chars / 2.5)` proxy per segment. Compare the same retained sections and periods first, then compare end-to-end fitting separately. A compact request may preserve more data near a budget boundary, so track both token delta and evidence retained. Provider input tokens can also include returned search content. Measure changes to that portion from paired owner runs and never infer it from source count.

For standard short-context Sol pricing, estimate `(uncached_input × $2 + cached_input × $0.10 + output × $10) / 1,000,000 + $0.01 × billed_search_calls`, adding applicable cache-write charges where reported and accounting for search content at model rates without counting the same input twice. Reasoning tokens are an output breakdown and should be tracked without adding them again to billed output. Existing telemetry estimates token costs with configured model prices and adds one configured fee for each web event, so that estimate is unsuitable for exact billing reconciliation. [Sol model pricing](https://developers.openai.com/api/docs/models/gpt-6.2-sol) · [API tool pricing](https://developers.openai.com/api/docs/pricing)

At fully uncached rates with fixed output, removing 2,000 or 5,000 model input tokens would save about **$0.004 or $0.010** per analysis. The same cached-token deltas would save **$0.0002 or $0.0005**. Avoiding one confirmed billable search would save **$0.01** in tool fees plus any measured reduction in search-content tokens. These are sensitivities. For the reported inputs and outputs, the full-uncached token components alone would be about $0.0353 for فولاد and $0.0872 for غبهنوش, excluding tool fees and any separate search-content charges. There is insufficient data for a realized dollar-saving estimate for any of the three runs.
