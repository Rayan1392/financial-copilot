# مدیریت نسخه و انتشار

این سند قاعدهٔ شماره‌گذاری نسخه‌ها، قالب شرح تغییرات و مراحل انتشار ساپیو را تعیین می‌کند. مراحل فنی deploy (workflow، SSH، rollback) در [deploy-prod-ci.md](../deployment/deploy-prod-ci.md) آمده است.

## منبع واحد

| چه چیزی | کجا | چه کسی می‌نویسد |
|---|---|---|
| شمارهٔ نسخه و شرح تغییرات هر نسخه | [`CHANGELOG.md`](../../CHANGELOG.md) در ریشهٔ مخزن | ایجنت [release-manager](../../.claude/agents/release-manager.md) |
| تگ git هر نسخه | `vMAJOR.MINOR.PATCH` روی commitی از شاخهٔ `prod` | release-manager، فقط پس از ثبت نسخه در CHANGELOG |
| نسخه‌ای که کاربر می‌بیند | صفحهٔ `/releases` و پیوند «نسخهٔ x.y.z» در صفحهٔ نخست، نوار کناری دسکتاپ و موبایل | هنگام build از `CHANGELOG.md` ساخته می‌شود |

شمارهٔ نسخه جای دیگری نوشته نمی‌شود: نه در `package.json`، نه در csproj و نه در کد. سه قفل این هم‌خوانی را نگه می‌دارند:

1. **build:** فرانت‌اند `CHANGELOG.md` را از طریق `src/frontend/changelog.vite-plugin.ts` می‌خواند. اگر فایل نباشد، build شکست می‌خورد.
2. **تست:** `src/frontend/src/lib/release-notes/__tests__/changelog.test.ts` قالب فایل را بررسی می‌کند: نسخه‌ها نزولی، تاریخ‌ها معتبر، نام بخش‌ها مجاز، هر نسخه دست‌کم یک مورد و یک compare link، و واژه‌ها مطابق [واژه‌نامهٔ رابط کاربری](../ui-copy-glossary-fa.md).
3. **deploy:** مرحلهٔ «Verify tag matches CHANGELOG.md» در `.github/workflows/deploy-prod.yml` اسکریپت `ops/release/check-release-version.sh` را اجرا می‌کند. تگی که با بالاترین نسخهٔ منتشرشدهٔ CHANGELOG یکی نباشد، پیش از اتصال SSH رد می‌شود.

## شماره‌گذاری (Semantic Versioning 2.0.0)

نسخهٔ `1.0.0` نخستین نسخهٔ پایدار است (۱۵ آبان ۱۴۰۵، 2026-11-06). از این نسخه به بعد:

| بخش | کی بالا می‌رود | مثال |
|---|---|---|
| `MAJOR` | تغییری که کاربر یا یکپارچه‌سازی بیرونی را مجبور به تغییر رفتار کند: حذف یک قابلیت، تغییر ناسازگار API عمومی، تغییر مدل اشتراک | `1.4.2` → `2.0.0` |
| `MINOR` | قابلیت تازه یا تغییر محسوس رفتار که با گذشته سازگار است (بخش `Added`، یا `Changed` قابل‌توجه) | `1.4.2` → `1.5.0` |
| `PATCH` | فقط رفع اشکال، بهبود کارایی یا اصلاح متن، بدون قابلیت تازه | `1.4.2` → `1.4.3` |

با بالا رفتن یک بخش، بخش‌های سمت راست آن صفر می‌شوند. هر شماره فقط یک بار مصرف می‌شود؛ حتی اگر deploy آن شکست بخورد و کد عوض شود، اصلاح با شمارهٔ بعدی منتشر می‌شود. تنها استثنا شکست زیرساخت با همان کد است: در آن حالت workflow روی همان تگ دوباره اجرا می‌شود.

نسخه‌های `0.x` تاریخچهٔ پیش از نسخهٔ پایدارند و دیگر ادامه پیدا نمی‌کنند.

## قالب CHANGELOG.md

قالب [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) است و برنامه آن را می‌خواند، پس این قواعد اجباری‌اند:

- بخش `## [Unreleased]` همیشه بالای همهٔ نسخه‌ها می‌ماند، حتی اگر خالی باشد.
- عنوان هر نسخه دقیقاً `## [MAJOR.MINOR.PATCH] - YYYY-MM-DD` است، بدون پیشوند `v`. تاریخ، روز انتشار به میلادی است؛ برنامه آن را شمسی نمایش می‌دهد.
- زیر عنوان نسخه می‌توان یک جملهٔ خلاصه نوشت.
- بخش‌ها فقط این نام‌ها را دارند: `### Added` (امکانات تازه)، `### Changed` (بهبودها)، `### Fixed` (رفع اشکال)، `### Security` (امنیت)، `### Deprecated` (منسوخ‌شده)، `### Removed` (حذف‌شده).
- هر مورد یک خط `- ...` است، به فارسی و برای کاربر: «چه چیزی برای کاربر عوض شد»، نه نام کلاس، endpoint یا شمارهٔ feature.
- تغییرات کاملاً داخلی (refactor، ابزار، CI، مستندات) در CHANGELOG نمی‌آیند؛ جای آن‌ها پیام commit است. اگر تغییری داخلی اثر محسوسی برای کاربر دارد (مثلاً سرعت)، همان اثر نوشته می‌شود.
- پایین فایل برای هر نسخه یک compare link هست: `[1.1.0]: https://github.com/Rayan1392/financial-copilot/compare/v1.0.0...v1.1.0`، و پیوند `[Unreleased]` به `compare/v<آخرین نسخه>...develop` اشاره می‌کند.

## در طول توسعه

هر تغییری که برای کاربر دیده می‌شود، در همان commit یا PR که به `develop` می‌رسد، یک مورد زیر `## [Unreleased]` اضافه می‌کند. این‌طور در زمان انتشار چیزی فراموش نمی‌شود و فقط کافی است Unreleased به یک نسخه تبدیل شود.

## مراحل انتشار

ایجنت release-manager این مراحل را انجام می‌دهد؛ کاربر انسانی هم می‌تواند دقیقاً همین را دستی اجرا کند.

1. **آمادگی:** `develop` تمیز است و تست‌های مربوط سبزند. موارد `[Unreleased]` با `git log v<آخرین نسخه>..develop --no-merges` مقایسه می‌شوند و هر تغییر کاربرپسندِ جاافتاده اضافه می‌شود.
2. **تعیین شماره:** طبق جدول بالا از روی بخش‌های Unreleased (`Removed` یا تغییر ناسازگار → MAJOR، `Added` → MINOR، فقط `Fixed`/جزئی → PATCH).
3. **ثبت نسخه در CHANGELOG:**
   - عنوان `## [Unreleased]` می‌ماند و زیر آن خالی می‌شود؛ موارد آن زیر `## [X.Y.Z] - <امروز>` منتقل می‌شوند.
   - compare link نسخهٔ تازه اضافه و پیوند `[Unreleased]` به‌روز می‌شود.
   - بررسی: `bash ops/release/check-release-version.sh vX.Y.Z` و `npx vitest run src/lib/release-notes` (در `src/frontend`).
   - commit روی `develop`: `chore(release): vX.Y.Z`.
4. **رساندن به prod:** `develop` به `prod` merge و push می‌شود. push به `prod` به‌تنهایی deploy نمی‌کند.
5. **تگ:** روی همان commit نوک `origin/prod`:
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z: <خلاصهٔ یک‌خطی>" origin/prod
   git push origin vX.Y.Z
   ```
   push تگ workflow «Deploy prod tag» را اجرا می‌کند.
6. **تأیید:** اجرای workflow سبز شود (`gh run list --workflow deploy-prod.yml --limit 1`) و صفحهٔ `https://sapioai.ir/releases` نسخهٔ تازه را «نسخهٔ جاری» نشان دهد. اگر workflow به دلیل زیرساخت شکست بخورد، طبق [deploy-prod-ci.md](../deployment/deploy-prod-ci.md) عمل می‌شود.

## قواعد تگ

- فقط تگ‌های `vMAJOR.MINOR.PATCH` نسخه‌اند و هر نسخه دقیقاً یک تگ دارد. تگ دیگری (مثل `prod-<date>`) ساخته نمی‌شود.
- تگ منتشرشده جابه‌جا یا حذف نمی‌شود؛ اصلاح همیشه با نسخهٔ تازه است.
- تگ فقط روی commitی از تاریخچهٔ `prod` گذاشته می‌شود (workflow و اسکریپت سرور هر دو این را بررسی می‌کنند).
- push هر تگ `v*` یک deploy راه می‌اندازد. اگر روزی چند تگ تاریخی باید ساخته شود، اول workflow غیرفعال می‌شود (`gh workflow disable "Deploy prod tag"`)، تگ‌ها push می‌شوند، نبود اجرای تازه بررسی می‌شود و workflow دوباره فعال می‌شود (`gh workflow enable "Deploy prod tag"`).
